## 四、修两处「逐 symbol 扫全表」(重跑时才暴露)

重跑时进程累积 CPU 达 3980s(≈66 分钟当量)仍不结束, 而原轮只需 4 分钟。
逐段计时后定位到两处:

**① `get_bars` 命中缓存后仍全窗扫描** — `g[g["symbol"] == sym]` 对整窗 **151 万行**
做全列布尔扫描 × 2809 次 ≈ 42 亿次比较, **纯 CPU 烧**。
改为预热时 `groupby('symbol')` 一次建索引 ⇒ **0.076s -> 0.0008s/次(约 95x)**,
索引路径与布尔路径**逐行日期比对一致**。

**② `get_valuation` / `_h5i_fin` 逐条 SQL** — `valuation` 有 **1540 万行**,
单次约 **200ms**, 且**与写法无关**(双 CAST / 单 CAST / 不 CAST 都是 ~200ms,
瓶颈是**扫过整表本身**)。2809 只 ⇒ **约 11 分钟**, 是日常管道最大一笔固定开销。
新增 `prefetch_latest_snapshots()`: 用 `row_number() OVER (PARTITION BY symbol ...)`
一次取全市场最新一期 ⇒ **11.5s / 5812 只**, 之后每只是字典查表。
25 只实测 **5.84s -> 0.011s**, 全池 **10.9 分钟 -> 1.3 秒**, **逐字段等价**。

### 一个重要的弯路(留档)

我先试的是「按 symbol 记忆化」, **无效** —— pool 里 2809 个 canon **互不相同**,
每个 symbol 只被问一次, 任何按 symbol 的缓存都**必然全部未命中**。
**该改的是查询形态(逐条 -> 批量), 不是加缓存。**
教训: 看到「N 次慢查询」先问「这 N 个键是否重复」, 再决定加缓存还是改形态。

### 加速层的守卫(8 例)

加速最大的风险不是不够快, 而是**顺手改了语义**。新增
`tests/test_h5i_accel_equivalence.py` 锁三件事:

1. **前视防护**: 快照装的是「每个 symbol 最新一行」(今天口径), **历史回测绝不能命中**
   —— 否则是把今天的财报喂给过去的选股。新增 `_LATEST_SNAP_FROZEN`,
   `_select_hist` 主动置位; `_h5i_fin_uncached` 也只在 `as_of is None` 时命中。
2. **字段契约**: 实现时**踩到过** —— 我一度在批量路径多给了 `liab_ratio`,
   而逐条路径**刻意不注入**它(duck 原实现恒 None, 为迁移前后逐位一致暂不注入)。
   多给一个字段就会改变 `governance_score` 的输入, 已修并加守卫。
3. **索引路径 == 布尔筛选路径**, 逐行等价。
