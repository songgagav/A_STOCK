# 下一次重跑的性能改造计划（2026-09-14 定序）

> 触发条件：`pe_ttm` 链路修复后**必然要重跑**全套验证（敏感性 + 保真度 + 影子回测）。
> 本次（2026-09-13/14）实测到的代价：保真度全窗口一次 = 66 次全市场 PIT 选股 ≈ 3.5~5 小时，
> 其中绝大多数时间花在**与口径无关**的重复计算上。以下按优先级排列，先做收益最大、风险最低的。

## 现状与瓶颈（实测）

| 事实 | 数值 |
|---|---|
| 单次全池 PIT 选股 | 2018 年（池 ~1400 只）≈ 80s；2025-2026 年（池 ~2900~3000 只）≈ 260s |
| 一次保真度全窗口 | 66 次选股 ≈ 3.5~5h（单核占用约 186%，即内部已有一点并行，但主体串行） |
| 口径隔离代价 | `_pit_cache_path` 把 `_t{q}` / `_rf{mode}a{alpha}` 写进缓存名 ⇒ **任何口径变体都要重算整套选股** |
| 内存 | 单进程 PrivateMemory ≈ 1.1GB（`_val_frame` / `_fin_frame` 常驻） |

## 第 1 步（最重要）：把"截尾"移出缓存

**问题**：截尾只改变**融合项**，池子与旧复合 `base` 完全不变，但当前实现把它编进了缓存键，
导致每个截尾比例都要重算 66 次选股。

**改造**：
- `RotationSelector._select_hist` 已经返回完整的 `scored` 列表（含
  `signal/trend/govern/vol/mom_rev/liquidity` 与 `score`）。落盘为
  `data/pit/pool_snapshot/{day}_n{n}.parquet`，**同时保存**：
  掺入前的 `base`（即未经过 `_blend_fml` 的 `score`）、融合原始值 `fml`（来自
  `fusion_or_fml`，即 `cross_section_scores` 的 z）。
- 排序键（`prod_score` / `rf1` / 截尾 3·5·8·10·15% / 未来任何新方案）在**读取快照后**
  计算，`_blend_fml`、`_apply_fusion_rank` 改为"纯函数式"地作用在快照上。
- 缓存键只保留与池子真正相关的维度（`day`、`n`），不再含口径标签。

**收益**：敏感性测试从"每次 4 小时"降到**秒级**；本次这类 66 次全量只需算一次。
**风险/注意**：必须落盘 `fml` 原始值而非 rank，否则截尾无法在读取后复算；
`_blend_fml` 当前会**改写 `score`**，所以要额外存 base 供复算。

## 第 2 步：并行度（8 核）

**改造**：按日期分片，`ProcessPoolExecutor` 并行生成池快照（第 1 步的产物），
按核数线性收益（8 核理论 6~8 倍）。

**前置依赖（必须）**：并发读取的**重试 + 空表检测**。此前的并发实验出现过
`_load_bars_forward` 静默返回空表、进而用 1~2 只标的算均值的失真事故；
`_full_calendar` 的空结果缓存问题也是同一类。必须先把"空结果不缓存 + 只数校验 +
明确告警"补齐（item 8），否则并行只会放大静默错误。

**注意**：h5i 为 lmdb 单写多读，读并发本身安全；但每个 worker 会各自常驻一份
`_val_frame`/`_fin_frame`，8 worker 可能吃 8GB+，需限制 worker 数或显式共享。

## 第 3 步：中性化加速

**现状**：`factor_fusion._residualize` 对**每个因子各做一次 OLS**（设计矩阵含
`ln_size` + 一级行业哑变量），4 个因子就要解 4 次，且每次都要重建 30+ 列哑变量矩阵。

**改造**（两选一，先做前者，收益大可叠加）：
- 一次构造设计矩阵，用 QR 分解对 4 个因子的响应矩阵**一次性多元回代**；
- 行业哑变量改用 within-transform（按行业去均值）等价快速法，避免显式构造哑变量矩阵。

**收益**：中性化在每次打分的热路径上，预计单次选股降 15~30%。

## 第 4 步：池子预筛（**仅**敏感性测试启用）

**思路**：敏感性测试只关心"不同截尾比例/排序键之间的相对差异"，可先用廉价预筛
（如按 `base` 取前 600 只）缩小池子再算融合，成本再降一个量级。

**限制**：会改变池子成员，尤其影响"头部构成"类结论 ⇒ **只能用于敏感性探索，
不能用于正式验证**。做成显式开关（如 `SENS_POOL_TOPK=600`），并在产物里标注
"预筛口径"，避免与正式结论混用。

## 红线

- 正式验证（涉及上线决策）必须用**全池 + 独立缓存**，不得使用第 4 步的预筛口径。
- 第 1 步落盘的池快照必须能完整复算任意排序键；任何"读快照后还要重算池"的设计都算失败。
- 第 2 步的并行必须建立在 item 8（并发重试 + 空表检测）之上，否则收益买不到。
