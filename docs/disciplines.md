### `git push` 报 TLS 错: **本仓 `.git/config` 里的代理与 sslbackend** (2026-09-25 已修)

**症状**(实测):

```
git push origin main
  -> fatal: unable to access 'https://github.com/songgagav/A_STOCK.git/':
     TLS connect error: error:0A000126:SSL routines::unexpected eof while reading
```

**关键误导**: 同时 `Test-NetConnection github.com:443` 是 **True**,
`Invoke-WebRequest https://api.github.com` 返回 **HTTP 200**, 且 `github_api` 工具也正常 ——
**只有 `git push` 失败**。故很容易误判成"网络问题"或"GitHub 挂了", 白等。

**真因**(`git config --list --show-origin` 一眼看出):

```
file:C:/Program Files/Git/etc/gitconfig   http.sslbackend=schannel   <- 系统级, 正常
file:.git/config                          http.proxy=http://127.0.0.1:6696
file:.git/config                          https.proxy=http://127.0.0.1:6696
file:.git/config                          http.sslbackend=openssl    <- 覆盖了系统的 schannel
```

**本仓自己的 `.git/config` 里留着一条代理 + 一条 `sslbackend=openssl`**。
该代理端口**在监听**(pid 存在), 但它对 git 的 TLS 握手不工作 ⇒ 失败点在 TLS 层,
于是错误信息指向 "SSL routines" 而**完全不提代理** —— 这就是它的误导性所在。

**修法**(只动本仓, **不碰全局**):

```
git config --local --unset http.proxy
git config --local --unset https.proxy
git config --local --unset http.sslbackend     # 让系统级的 schannel 生效
```

**注意一个坑**: `git config http.proxy ""` **不解决问题** —— 实测设成空串后
`--local --get` 仍返回代理地址(空串在该键上不构成有效覆盖),
必须用 `--unset` 真正删掉。

**判据(下次遇到同类)**:
> 「网络看着正常, 只有某个工具连不上」时, **先查那个工具自己的配置**,
> 而不是先怀疑网络。用 `git config --list --show-origin` 看**每一层的来源**,
> 而不是只看 `--get` 的最终值 —— 最终值会掩盖"是哪一层设的"。

### 「网络看着正常但 git 连不上」有**两种**可能 —— 不要一概归因到配置

> 用户 2026-09-25 指出: 这两次形态不同, **不能一概归因**。
> 一概归因的代价是**改配置去修一个本来会自愈的问题** —— 而配置改动会留下来,
> 下次再出问题时多一个变量要排除。

| 症状 | 真因 | 处置 | 依据 |
|---|---|---|---|
| `TLS connect error: ...unexpected eof while reading` + `SSL routines` | **本仓配置**: `.git/config` 里的代理 + `sslbackend=openssl` 覆盖 | **改配置**(`--local --unset`) | `Test-NetConnection github.com:443` = **True**, 且 `api.github.com` HTTP **200** ⇒ 网络通, 是 git 自己的 TLS 参数错 |
| `Could not connect to server` / `Recv failure: Connection was reset` | **传输层波动** | **重试**(实测第 2~3 次即成功) | 同上, 网络探测通; 但 git 连 `github.com:443` 超时/被重置 |

**两次的实测对照(2026-09-25, 同一个仓库同一天都发生了)**:

```
现象 A: TLS connect error: error:0A000126:SSL routines::unexpected eof while reading
        -> 真因: .git/config 的 http.proxy=127.0.0.1:6696 + http.sslbackend=openssl
        -> 修法: git config --local --unset ...        (一次性, 永久解决)

现象 B: Failed to connect to github.com:443 after 21151 ms / Connection was reset
        -> 真因: 传输层波动
        -> 修法: 重试(第 2 次成功)                      (自愈, 不要动配置)
```

**可操作判据(先分类, 再动手)**:

> 1. **看错误文本的关键词** —— `SSL routines` / `TLS` 指向**配置**;
>    `Could not connect` / `Connection was reset` 指向**传输层**;
> 2. **两者都用同一条网络探测区分**: `Test-NetConnection github.com:443` 与
>    `Invoke-WebRequest https://api.github.com`。**若网络通, 就不是网络问题**;
> 3. **传输层波动先重试**(2~3 次, 间隔几秒), **成功了就不要改配置** ——
>    否则你会把一个自愈问题"修"成一个持久的配置差异;
> 4. **`api.github.com` 通但 `github.com:443` 不通是可能的**
>    (不同的 IP/路径), 故"某个 GitHub 端点通"不能推断"git 的端点也通"。

### `git commit -F` 报 **`a NUL byte in commit log message not allowed`** (2026-09-26 实测)

**症状**: `git push` 前一步就失败, 报

```
error: a NUL byte in commit log message not allowed.
fatal: failed to write commit object
```

紧接着 `git push` 会说 `Everything up-to-date` —— **因为根本没有提交产生**。
**这正是 ③「前置状态没造出来」的现场**: 后续步骤在操作一个**不存在的提交**,
而它的报错信息(`up-to-date`)看起来像"已经推过了"。

**真因**: 用 PowerShell 的 `Set-Content -Encoding utf8` 写提交信息文件时,
**UTF-16 内部表示被写出**, 产生 NUL 字节。`git` 拒绝 NUL。

**修法(一次到位, 不要再试 `Set-Content`)**:

```powershell
$m = @'
...(提交信息)...
'@
[System.IO.File]::WriteAllText("$PWD\.git\CM.txt", $m,
    (New-Object System.Text.UTF8Encoding($false)))   # $false = 不写 BOM
git commit -F .git\CM.txt
```

**自查(建议每次都做, 一行)**: 写完先验字节, 再提交 ——

```powershell
$b = [System.IO.File]::ReadAllBytes("$PWD\.git\CM.txt")
"bytes=$($b.Length) NULs=$(($b | Where-Object { $_ -eq 0 }).Count) BOM=$($b[0] -eq 0xEF)"
```

**同族**: 这与 §6.12 的「`Out-File -Encoding UTF8` 给开关文件写出 BOM」
是**同一个根因**(PowerShell 的编码默认值与"无 BOM UTF-8"不一致),
已出现两次。**判据见下一节**。

### 「凡要交给别的程序读的文件, 写完都验一次首字节」(2026-09-26 固化)

> **判据**: 凡是**写给别人读**的文件(开关 / 配置 / 提交信息 / JSON 清单 /
> 给子进程的输入), 写完之后**先验首字节, 再交付**:
> `bytes` / `NULs` / `BOM` 三项。
>
> **为什么**: "我写对了内容"与"**文件字节正确**"是**两件事** ——
> 而第二件才是别的程序实际读的东西。

**本仓已实测两次, 根因同一个**(PowerShell 的编码默认值 ≠ 无 BOM UTF-8):

| # | 日期 | 操作 | 实际写出 | 后果 | 发现方式 |
|---|---|---|---|---|---|
| 1 | 2026-09-25 | `Out-File -Encoding UTF8` 写 `data/backfill_switch.json` | **带 BOM** | `utf-8` 读时抛 `Unexpected UTF-8 BOM`, 被 `except` 吞掉 ⇒ **开关被静默读成"未配置"** | 用 `utf-8-sig` 读才复现 |
| 2 | 2026-09-26 | `Set-Content -Encoding utf8` 写 `git commit -F` 的信息文件 | **含 NUL** | `git` 拒绝 ⇒ **提交根本没产生**; 而紧接着的 `git push` 报 `Everything up-to-date`(看起来像已推过) | 字节三连验出 `NULs>0` |

**两次都属于"报告说成功、东西其实没生效"** —— 与 DISC-2 要防的形态同源。
故这条不是"编码小知识", 而是**交付前的最后一道闸**。

**一次性做对(推荐写法)** —— 绕开 PowerShell cmdlet 的编码默认值:

```powershell
# 写: .NET 直写, 显式指定"无 BOM 的 UTF-8"
[System.IO.File]::WriteAllText($path, $content,
    (New-Object System.Text.UTF8Encoding($false)))     # $false = 不写 BOM

# 验: 交付前一行, 三项一起看
$b = [System.IO.File]::ReadAllBytes($path)
"bytes=$($b.Length) NULs=$(($b | Where-Object { $_ -eq 0 }).Count) BOM=$($b[0] -eq 0xEF)"
```

**读的那一侧也要防御**(因为文件可能不是本仓写的):

- 读本仓自己写的配置 ⇒ **一律用 `encoding="utf-8-sig"`**
  (它能同时读带 BOM 与不带 BOM, 而 `utf-8` 遇到 BOM 会抛异常);
- **不要把"读失败"吞成默认值** —— 第 1 次实测就是被 `except` 吞掉,
  才变成"静默读成未配置"。**读失败要留下痕迹**(与 DISC-1 的留痕纪律同族:
  **要么如实、要么留空、不许猜**)。

**推广**: 这条与 `data/` 那些运维文件**互相加重** ——
运维预案越成熟, 写 `data/` 的文件越多, "编码/字节"这类问题的暴露面越大。
故**每次新增一个"人写、程序读"的文件, 都要同时写它的字节验收方式**。

> **⚠️ 写这一节时又踩了一次"守卫自指涉"(本会话第 5 次)**: 我原本在这段里
> **引用了** DISC-1 那条"留痕字段要么如实、要么留空、**不许猜**"原则的**原句**,
> 而 `test_rule_explains_why_guessing_is_worse` 等两条守卫是用
> **`src.find(那句原句)`** 来**定位 DISC-1 那一节**的 ——
> 我的引用**出现在更靠前的位置**, 于是守卫把我这段当成了 DISC-1 的正文,
> 切片窗口落空 ⇒ **2 条 DISC-1 守卫失败**。
>
> **这正是「识别条件必须覆盖该节所有可能格式」的实例**: 用**子串首次出现**定位
> 一节, 会被任何**更靠前的引用**劫持。故此处**不再引用原句**(改用同义描述),
> 并把这条教训记在这里 —— 因为"引用某节的关键句"是写文档时的**自然冲动**,
> 后面还会再犯。
>
> **修法方向(留给后人)**: 这类守卫应改为**按小节标题定位**(行首锚定),
> 而不是按"某句关键话的首次出现" —— 后者**本质上会被引用劫持**。

## DISC-1: 价格衍生指标**取自源, 不得自算**

**状态**: 已固化(2026-09-22)。**执行机制**: 三层强制 + 6 例守卫。

### 事实依据(不是理论担忧)

实测 **600177 @ 2026-09-18**(含除权): 前一日 close = **8.30**, 当日 close = **8.14**。

| 来源 | 涨跌幅 | 判定 |
|---|---|---|
| **自算** `(8.14/8.30 - 1)` | **−1.93%** | 用**未调整**前收 ⇒ **错** |
| **引擎** `pct_chg` | **+0.49%** | 基于除权调整后 `pre_close = 8.10` |
| **baostock** `pctChg` | **+0.4938%** | 与引擎一致 |

### 为什么这条必须成为纪律(而不是"注意一下")

1. **错得很像对的**: `−1.93%` 是一个**完全合理的涨跌幅** —— 不抛异常、不越界、
   看起来毫无可疑。它只会让当天所有价格衍生因子**悄悄偏掉**。
2. **只在除权日发生**: 无除权事件的区间上, 自算与取自源**完全相同** ——
   所以**用近端样本 / 小样本验证测不出来**。这正是本仓反复出现的
   "小样本验证通过、上线才炸"。
3. **影响面是全局的**: 涨跌幅进入动量/反转类因子, 再进入打分与排序 ——
   一天的偏差会污染当日全部选股结论。

### 原则

1. **任何可由价格推导的量, 一律取自数据源**: 涨跌幅、换手率、复权因子……
2. **理由**: **只有源知道除权/停牌/复牌这些事件**; 从价格反推**永远缺这部分信息**。
3. **缺字段时宁可响亮失败**, 不得"缺了就自己算" —— 前者是立刻可见的故障,
   后者是静默的错误数据。

### 执行机制(三层强制, 缺一层就会漏)

| 层 | 机制 | 落地 |
|---|---|---|
| **① 请求层** | 必需字段集缺任何一个 ⇒ **直接 `ValueError`** 并说明原因 | `baostock_adapter.REQUIRED_FIELDS = (pctChg, turn, preclose)`; `make_baostock_fetcher` |
| **② 映射层** | 每个源的 `field_map` 必须把源的涨跌幅列映射到 `change_pct`; 且归一化层**禁止**出现价格推导 | `bars_ingest.SOURCE_SPECS`(baostock `pctChg` / akshare `涨跌幅` / 引擎 `pct_chg`); 静态扫描禁 `pct_change(` / `shift(1)` / `pct_chg =` |
| **③ 校验层** | 交叉校验逐值比对 `change_pct`, 并有**反证用例**证明判据有效 | `cross_validate`; `test_selfcomputed_value_would_be_caught`(自算的 −1.93 **必须**被判不一致) |

**为什么是三层而不是一层**: ① 防"取数时就漏了字段"; ② 防"取到了但没映射, 下游自算";
③ 防"判据形同虚设"(只声明规则、却没有任何东西验证规则真的会触发)。

### 守卫清单

`tests/test_baostock_adapter.py::TestFactorComputationDiscipline`

- `test_fetcher_requests_the_derived_fields` —— 字段集必须含必需字段
- `test_fetcher_refuses_to_run_without_them` —— 缺字段 ⇒ `ValueError`(不是静默)
- `test_baostock_spec_maps_change_pct_from_source` —— 映射必须来自源列
- `test_all_sources_that_have_the_field_declare_it` —— **通用化**: 将来接新源也自动被检查
- `test_normalize_never_derives_change_pct` —— 静态扫描禁止价格推导
- `test_selfcomputed_value_would_be_caught` —— **反证**: 自算值必被抓获

### 同族纪律: 单位也必须是**写死的等式**

`cross_validate.EXPECTED_VOLUME_RATIO` 把每源相对基准的成交量比值**写死**:

| 源 | 预期比值 | 依据 |
|---|---|---|
| `stockdb_sdk` | **1.0** | 基准自身 |
| `baostock` | **1.0** | 单位是**股**(实测 min=max=mean=**1.0000**) |
| `akshare` | **100.0** | 单位是**手**(实测 mean=**100.0001**) |

**为什么是"写死的等式"而不是"看着接近"**: 哪天某源悄悄改了单位(股 ↔ 手),
比值会跳到 100 —— **等式立刻不成立**; 而"看着接近"什么都不会发生。
反证用例: `test_volume_off_by_100x_fails_loudly`(差 100 倍必被抓获)。

> 注: 手→股换算**不是精确 100 倍** —— 手是整数单位, 会截掉不足 1 手的部分
> (实测同一只同日聚宽 532667 手 vs 引擎 53266728 股, 差 28 股)。
> 故换算后允许 ≤100 股(1 手)的差; 这与"比值预期 = 100.0"不矛盾。

### 同族纪律: 留痕字段**宁可 None, 不猜** (2026-09-25)

DISC-1 管的是"**取数**不得自算", 本条管的是"**记账**不得自造" —— 同一个立场的两面:
**凡是要被别人当依据的东西, 都必须是它本来的样子。**

判据:

> **留痕/上报里的每一个字段, 取不到就写 `None`(并说明取不到),
> 绝不用"估计/上一次的值/看着像的那个"补上。**

依据(2026-09-25, 回填留痕):

`baostock_backfill._append_provenance` 要记两个字段 —— 回填后的 h5i 水位、
当时的引擎数据日。两者的正确写法都是**取不到就 None**:

```
engine_day_at_backfill: "2026-09-22"   # 取到了
h5i_watermark_after:    "2026-09-24"   # 取到了
# 取不到时: None  —— **不是**"用回填的那天顶上", **不是**"沿用上次的值"
```

**为什么猜一个日期比写 None 危险得多**: 留痕是**事后追溯的唯一依据**。
一个猜出来的日期会被后来的人**当成事实**, 并据此推出"当时引擎已经到那天了"
这种**完全错误**的结论 —— 而错误的事实**比缺失的事实更难纠正**, 因为它看起来是证据。

**为什么不做"沿用上次值"(last-known)**: 那在有状态的服务里是常见做法, 但留痕**不是**
遥测 —— 遥测的"上次值"有明确时间戳可辨; 留痕的字段会被当成"那一刻的事实"读。
**一条带时间戳的 None, 信息量高于一条不带时间戳的猜测。**

**可操作的自检**: 写任何留痕字段时问
「**这个值我是"读到的"还是"推出来的"?**」 —— 推出来的一律改 None,
并在同一条记录里说明为什么没读到。

**同类先例**: `_engine_day()` / `_h5i_watermark()` 都实现了"异常/缺字段一律返回 None"
并有守卫(`test_helpers_never_invent_a_date` / `test_helpers_tolerate_exceptions`),
其中前者还专门断言**格式不对的日期**(`"bad"`)也返回 None —— 半个日期同样不如 None。

### 如何应用于新数据源(检查表)

接一个新源时, 逐条确认:

- [ ] 该源是否提供涨跌幅字段? 字段名是什么?
- [ ] 已写进 `field_map` 映射到 `change_pct` 了吗?
- [ ] 换手率(`turnover`)呢?
- [ ] 该源的复权口径与本仓(`不复权`)一致吗? **必须用含除权的区间验证**
      (找法: 引擎 `pre_close != 前一交易日 close` 即该日除权)
- [ ] 单位是否声明并实测过? (实例: akshare 成交量是**手** ⇒ ×100; baostock 是**股** ⇒ ×1)
- [ ] `cross_validate` 对该源的 `volume_ratio` 预期是**写死的等式**, 不是「看着接近」?

## DISC-2: **检查项静默消失** 与 **检查失败** 必须可区分

> ### 共同原则: **依赖一次对照, 不依赖注意力** (2026-09-25)
>
> 下面六种形态看着各不相同, 但**对抗它们的方法只有一个**: 把判据从
> 「我有没有注意到」换成「**某个确定性动作有没有发生**」。
>
> **为什么必须这样**: 注意力是**会耗尽**的资源, 而且它耗尽时**不报警** ——
> 你只是不再检查了, 而报告一切正常。这与本纪律要防的东西**是同一个病**:
> 失效不留痕迹。所以任何"靠更小心就能防住"的说法都等于没防。
>
> 对照则是**一次性的机械动作**: 做了就是做了, 结果非真即假, 不需要保持警惕。
>
> | 形态 | 「靠注意力」的说法(❌) | 「一次对照」的做法(✅) |
> |---|---|---|
> | ① 假信心测试 | "断言要写强一点" | **喂一个坏样本, 看它是否失败**(跑一次就有答案) |
> | ② skip 被读成通过 | "注意别漏看 skip" | **数 skip 并逐条问"它何时会真跑"**(可枚举) |
> | ③ 前置状态没造出来 | "写用例时小心点" | **先断言前置条件**(不成立就立刻红) |
> | ④ 测试固化错误规格 | "判据要想清楚" | **问"这个数字从需求推的还是从实现反推的"**(二分) |
> | ⑤ 归因在中间层丢失 | "传参时仔细核对" | **抄下承接方认的字段名/类型, 逐字比**(可机械执行) |
> | ⑥ 降级过程无告警 | "多留意中间状态" | **列出每个档位, 逐档问"谁负责叫"**(可枚举) |
>
> **五个已经付出过代价的实例**(每一条都不是推演):
> · 我在**修别人 ⑤ 的同时**, 在自己新写的约 200 行代码里犯了**三次** ⑤ ——
>   说明它与认真程度无关, 只与"有没有做那次对照"有关;
> · 一次 stdout 截断让结论字段全丢, 导致**多跑两次 30 分钟的全市场取数** ——
>   "结论落盘成文件"就是那次对照;
> · 全量测试一度报 **382 errors**, 单跑该文件却 12 passed ——
>   对照(单跑 vs 全跑)立刻定位为测试基建残留, 而非代码问题;
> · `TableStale24h` 曾 **firing 330 次**而无人处理 —— 长期靠注意力盯着的告警,
>   等价于没有告警。
> · **守卫依赖了版本控制之外的机器本地状态**(2026-09-25, 见下) ——
>   它**通过了所有本地验证**, 却在"按预案执行操作"的那一刻变红。

> #### 实例: 断言依赖 <u>gitignored 的机器状态</u> (2026-09-25)

> #### 追加判据: **一条证据若能同时支持两个互斥假设, 它就不构成确认** (2026-09-26)

> **这条已升格为正式形态 ⑦「证据无判别力」** —— 详见「详细判据」一节。

>
> #### 守卫的设计原则(与上面六种形态并列, 但管的是"怎么写守卫")
>
> > **守卫要守「不变量」, 不要守「实现细节」。**
>
> 这是六种形态之外的**设计**约束 —— 前者说的是"守卫可能怎么失效",
> 这条说的是"怎么写才不容易失效"。
>
> **为什么它重要**: 守实现细节的守卫会在**每次正常演进**时被撞到,
> 然后被人"顺手"放宽; 放宽几次之后它就只剩装饰作用了 ——
> 而**它还在跑、还在通过**, 于是没人觉得它坏了。这是 ① 假信心测试的**制造过程**:
> 没有人一开始就想写个没用的守卫, 是**一次次迁就**把它变成没用的。
>
> **实例(2026-09-25)**: `test_no_single_threshold_for_all_tables` 的**本意**是
> "禁止用单一阈值打所有表"; 我在同一天把日报类拆成三档(数据商 / 引擎喂数 / 季报)。
> 若这条守卫写的是**"必须恰好两条规则"**(实现细节), 它当场就会被撞到,
> 而正确的反应**不是**改守卫而是理解它的不变量 ——
> **"分档可以更多, 但不能退回单一阈值"**。守卫本身不用改, 照旧通过。
>
> **判断方法(一句话)**:
> 问「**这条断言, 在功能正常演进时会不会被撞到?**」
> · 会被撞到 ⇒ 它守的是实现细节, 该改写成不变量(或换成"档数 ≥ N 且判据互不相同"这类);
> · 不会 ⇒ 它很可能真的在守不变量。
>
> **配套的三道保险**(与 ⑥ 的「守卫自指涉」配套):
> 1. **判据里不要出现"用来解释守卫的话"** —— 模式串与提示文本分开写;
> 2. **守卫必须声明它排除了什么**, 且排除范围要能在断言文本里看见;
> 3. **加一条"扫描量下限"断言** —— 防止判据意外变窄后安静地"全部合格"。

> #### 守卫的设计原则之二: **识别条件必须覆盖该节的所有可能格式** (2026-09-26)
>
> > **写"识别/排除条件"时, 先问: 「这一节可能出现哪些格式? 我覆盖了几种?」**
> > 只覆盖**当时**那一种 ⇒ 结构一演进, 守卫就静默失效或反向误报。
>
> **为什么它必须成为纪律**: 同一个坑我在**两天内踩了三次**(每一条都是实测):
>
> | # | 识别条件写的是 | 结构怎么变的 | 后果 |
> |---|---|---|---|
> | 1 | 按**源码文本**找 `yaml.safe_load` | 守卫自己的 docstring 里也有这串字 | **报了自己**(良性: 报错可见) |
> | 2 | 「用没用 PyYAML」看函数体是否含 `_load_rules(` | 另一守卫的**测试样本串**里也含它 | **误报样本**(良性) |
> | 3 | 叙述区 = **`>` 开头的块** | 病历从 `>` 块**搬进正文** `### ⑦` 小节 | **反向误报**: 守卫去报**病历** |
>
> 三次的**根因是同一个** —— 我把"识别条件"写成了**当时文档的偶然形状**
> (某个前缀、某个函数名、某个位置), 而不是"这一节在语义上是什么"。
>
> **必须用"语义特征"而不是"位置/字面量"**:
>
> | ❌ 位置/字面量(会腐烂) | ✅ 语义特征(较耐久) | 但仍要配覆盖检查 |
> |---|---|---|
> | "`>` 开头的行" | "**引用错误的那几行**" | 二者取并集, 并断言并集非空 |
> | `find("### 四种")` | `find(_DETAIL_HEADING)` + 断言恰好一次 | 见 ④b |
> | 函数体含某串 | **AST 调用节点**而非文本 | 见 ① 的 docstring 实例 |
>
> **落地要求(两条, 缺一不可)**:
>
> 1. **枚举该节的可能格式** —— 写识别条件时, 在注释里**列出**你考虑过的格式
>    (本次: `>` 块 / 正文小节 / 表格行 / 多行字符串), 并说明为什么覆盖或不覆盖;
> 2. **加一条"识别区非空"的反向验证** —— 断言识别出的区域**确实有内容**
>    (本次: `test_the_narrative_regions_are_detected` 要求至少一行叙述真的引用了
>    「误报」, 且 ⑦ 小节与所有 `>` 行都被标进叙述区)。
>    **没有这条, 识别条件可能悄悄变成"识别一切"或"识别不到任何东西"** ——
>    前者让主断言变空, 后者让它恒真。**两种都是"看起来在检查"。**
>
> **与 ④b 的分工**: ④b 管**切片边界**(标识还在吗), 本条管**识别条件**
> (格式覆盖全吗)。二者常同时出现: 本次三个用例既按已改名的标题切片(④b),
> 又只认 `>` 块这一种格式(本条)。

> **排查入口(先读这一行)**: 遇到「报告看起来正常, 但可能有问题」时,
> **先读紧接着的「失效形态索引」** —— 它把本纪律的 **6 种形态**连**排查优先级**
> 与**检查方法**列成一张表, 用于决定**先查哪几种**。
> **不要**从后面的实例表逐条读起: 那是"曾经发生过什么"的**档案**, 不是排查顺序;

### 失效形态索引(排查时先看这里)

遇到「报告看起来正常, 但可能有问题」时, 按本表决定**先查哪几种**。
详细判据与实例见下一节「详细判据」。

**优先级 = 该形态「有多难被发现」x「发现不了有多贵」**,
不是"有多常出现" —— 常见的形态反而容易在过程中自然暴露。

| 形态 | 排查优先级 | 检查方法 | 漏掉它的后果 |
|---|---|---|---|
| **⑥ 降级过程无告警** | 🔴 **高** | 检查**每一个中间档位是否都有告警**; 列出各档触发条件, 找"没人管"的区间 | 系统**正确地**降级却无人知晓, 一路滑到停手才发现 —— 根因已无从查证 |
| **⑤ 归因在中间层丢失** | 🔴 **高** | **检查承接方到底认哪个字段**(不是"检查自己有没有出错") —— 对照字段名/类型/管道; 搜索字段投影 `{k: {"ok":…, "rows":…}}` | 错误信息指向错误方向 ⇒ **朝反方向投入时间** |
| **⑦ 证据无判别力** | 🔴 **高** | 对每条"确认"问「**它能否区分那两个互斥假设? 反过来才是真的, 它会不一样吗?**」不一样才叫证据 | 把**未经验证**的判断当既成事实写进注释/登记册 ⇒ **后来的人也照错** |
| **④ 测试固化了错误规格** | 🔴 **高** | 检查判据是否用**业务事实**而非**实现算术**; 找"实现里刚好 +1/减一/两倍" | 全绿但规格是错的 ⇒ 缺陷被**当成规格**长期锁住 |
| **④b 边界腐烂** | 🔴 **高** | 检查每个"按标识切片"的地方: 那个**标识字面量还在吗**? 加一条「**它恰好出现一次**」的闸门 | 标识一改名 ⇒ `find` 返 -1 ⇒ 切片跑到文末 ⇒ **反向断言恒真**(报告更绿) |
| **③ 前置状态没造出来** | 🟡 中 | 检查每个用例是否**先断言前置条件**再造被测动作 | 用例在验证一个**与它名字无关**的场景 |
| **③b 前置是环境事实** | 🟡 中 | 检查断言依赖的东西**是否都在版本控制里**(`data/`、`logs/`、环境变量、壁钟) | 前置被**正常运维操作**改掉 ⇒ 守卫在**代码正确**时变红, 而最省事的处置是**放宽它** |
| **② skip 被读成通过** | 🟡 中 | 检查 `skip` 数与其**原因**; 问"它在什么条件下会真跑" | 一条关键用例**从未执行**, 却计入通过 |
| **① 假信心测试** | 🟢 低 | 检查断言强度; 问"喂一个坏样本, 它会失败吗" | 断言太弱 ⇒ 永远通过(但**换坏样本就能发现**) |

**为什么 ④/⑤/⑥/⑦ 优先**: 它们是那几种**"所有信号都指向正常, 而实际情况相反"**的形态 ——
① 断言弱(换个坏样本就露馅)、② skip 有计数可见、③ 前置可以补断言,
③b 甚至**自己会红**(只是红得让人误解方向),
这四种只要**看一眼原始报告或加一个反证**就能发现。
而 ④ 的测试**正确地在验证一条错的规定**(全绿且无异常可查),
⑤ 的错误信息**本身就是误导性的**(越认真读越可能走错方向),
⑥ 则连"系统做得对不对"都不必问 —— **它做得完全正确, 只是没人知道**;
⑦ 更彻底: **它连"错了"这个状态都不产生** —— 判断被当成了事实,
于是没有任何后续环节会去质疑它。**它污染的不是过程, 是<u>结论</u>。**
故它们只能靠**主动的元检查**发现:

- 对 ④: 问「**这个数字是我从需求推出来的, 还是从实现反推出来的?**」
- 对 ⑤: 问「**这条错误信息, 有没有一个独立数字能证伪它?**」
- 对 ⑥: 问「**从健康到停手之间有几个档? 每个档分别由哪条告警负责?**」
- 对 ⑦: 问「**如果反过来才是真的, 这条证据会不一样吗?**」

**可自动化程度**(决定哪些能进 CI): ①②③③b 基本可由测试度量/守卫覆盖
(③b 尤其容易静态化: 断言"不依赖 gitignored 路径"即可);
④/④b 只能靠**判据来源与边界标识的复核**(人的元检查, 但 ④b 的闸门可自动化);
⑤ 可以用"投影点审计"部分自动化(本仓已修的两处都是 `{k: {"ok":…, "rows":…}}` 这种字段投影);
⑥ 可以**完全自动化** —— 把"每个档位都必须有告警"写成守卫即可(见下节 ⑥ 的对策);
⑦ **无法自动化** —— 它问的是"这条证据的<u>逻辑效力</u>",
机器判不了"两个假设是否互斥"; 只能在写结论时人工过一次那个问句。


### 事实依据(本会话**六次**独立出现, 不是理论担忧)

### 关于「假信心测试」: `skip` 不等于 `通过`

上表第 5 条单列出来, 因为它最容易被忽略:

- pytest 的默认报告里 **`skipped` 与 `passed` 都是绿的** —— 一个"因环境缺依赖
  而从不执行"的用例, 在概览上与"执行且通过"**看起来一样**;
- 判据: **任何带 `pytest.skip` 的用例, 都必须有人能回答"它在什么条件下会真跑"**;
  若答案是"永远不会", 那它不是测试, 是**装饰**。
- 本仓对策: 关键路径的真实数据用例必须**用生产同款加载路径**
  (如 `engine_bars_sync.load_rd()` 而不是裸 `from stock_sdk import rd`),
  使其在目标环境下**真的执行**; 并在核实结果时**专门看 skip 数**
  (本会话多次出现"测试全绿"而其中若干条其实在跳过)。

### 详细判据: 四种"测试看起来正常" + 三种"问题不在测试里"

前四种是**测试**层面的失效 —— 单靠"测试全绿"无法区分它们。
后三种坏的不是测试: ⑤ 坏的是**发现问题之后往哪儿查**(排查方向),
⑥ 坏的是**根本没人被通知**(告警覆盖),
⑦ 坏的是**证据本身的效力**(它压根分不开两个假设)。
放在一起是因为它们的**共同点**都是"让报告显得正常", 而**该修什么**各不相同:

| 形态 | 现象 | 该修什么 |
|---|---|---|
| **① 假信心测试** | 断言太弱, **永远通过** | 加强断言 / 加**反证用例**(喂坏样本必须失败) |
| **② skip 被读成通过** | 用例**从未执行**(缺依赖/缺环境) | 让它在目标环境下真跑, 或明确它永不跑=装饰 |
| **③ 前置状态没造出来** | 测试**跑了、断言也"对"了** —— 但它在验证一个**错误的场景** | **先断言前置条件**, 再造被测动作 |
| **③b 前置是环境事实** | 前置本身没问题, 但它**依赖了版本控制之外的东西**, 于是被**外部**改掉 | 把前置从**环境事实**改成**显式输入**(参数注入) |
| **④ 测试固化了错误规格** | 测试**完全正确地在验证一条错的规定**, 全绿 | 判据改用**业务事实**, 不用**实现算术** |
| **④b 边界腐烂** | 用例按一个**字符串标识**切片(`src[i:src.find("### X")]`), 而该标识**已被改名/删除** | 标识**集中成常量**, 并加「**恰好出现一次**」+「切片占幅合理」两道闸门 |
| **⑤ 归因在中间层丢失** | 错误信息**把排查者引向错误方向** | **保留每层的 error 字段**; 用"独立反证"验真因 |
| **⑦ 证据无判别力** | 拿一条**对两个互斥假设都成立**的证据, 当成对其中一个的确认 | 问「**反过来才是真的, 这条证据会不一样吗?**」不会 ⇒ 去找能**区分**两者的观测 |

**③ 为什么最隐蔽**: 它既不是 skip、也不是断言失败 —— **表面完全正常**。
实例(本会话): 我写"已提交但未推送"的用例时忘了改文件内容,
于是 `git add` 之后**没有内容变化 ⇒ 空提交 ⇒ 根本没产生提交**,
`ahead` 停在 0 而断言`== 1` 失败 —— 看起来像"被测代码不报未推送",
实际是**我压根没造出'未推送'这个状态**。

**判据(③ 的通用对策)**:

> **在断言"结果"之前, 先断言"场景已成立"。**

例如: 要在"已提交未推送"上做断言, 就先断言 `git status` 干净 **且** 已有一次新提交;
要在"文件缺失"上做断言, 就先断言该文件确实不存在。
否则整条用例可能在验证一个与它名字无关的场景。

#### ③b 前置是**环境事实**: 前置没问题, 但它依赖了版本控制之外的东西

③b 与 ③ **并列** —— 两者的表现都是"测试在验证一个与它名字无关的场景",
但**成因与修法不同**:

| | ③ 前置状态没造出来 | **③b 前置是环境事实** |
|---|---|---|
| 前置怎么没的 | 测试**自己没造**(漏了那一步) | 测试**没造过** —— 它**假设**环境里本来就是这样 |
| 谁改变了它 | 没人; 它从头到尾不存在 | **外部**, 而且是**正常操作**(如按运维预案建了个文件) |
| 表现 | 用例在验证错误的场景 | 用例**红了**, 但代码**完全正确** |
| 修法 | **先断言前置条件** | 把前置从**环境事实**改成**显式输入** |

**实例(2026-09-25, 真实事故)**: `TestDefaultOff::test_disabled_by_default`
断言 `BT.is_enabled({}) is False` —— 隐含前提是「**这台机器上没有开关文件**」。
而开关文件 `data/backfill_switch.json` 在 `data/` 下, **`data/` 是 gitignored 的**。
当天我**按自己写的 09-28 预案**把它建成 `{"enabled": true}` ⇒
`{}.get(ENABLED_ENV)` 返回 `None` ⇒ 代码按设计**回落到读开关文件** ⇒ 返回 `True`。

**实测现象**: 全量测试从"全绿"变成 **2431 passed / 1 failed**, 且
**代码一行都没改**, 前一天还是绿的 —— 这正是它最容易让人误判的地方。

**这不是回归, 是"按预案正常操作"把一个隐性前置条件打掉了。**
代码行为完全正确; 错的是断言把"没有配置"当成了**环境事实**而非**显式输入**。

| 维度 | 详情 |
|---|---|
| 危害等级 | **高** —— 不是"测试写松了", 而是**守卫会在正确操作下变红** |
| 为什么会误导人 | 失败信息指向"默认值不对", 诱导人去改**代码**; 而代码是对的 |
| 真正的代价 | 若不追到根因, 最可能的处理是**放宽断言**(等于删掉这条守卫) —— 正是「守卫的设计原则」描述的退化过程 |

**修法(③b 的通用对策)**:

> **把"没有配置"从环境事实改成显式输入。**

本次的具体做法: 传入一个确定不存在的 `switch_fp=tmp_path/no_such_switch.json`;
文件路径本身的行为由另一个用例(`TestSwitchFileBecauseEnvAloneIsNotEnough`)
用真实 tmp 文件覆盖。

**可操作判据**:

> 问「**这条断言依赖的任何东西, 是否都在版本控制里?**」
> 不在(开关文件、`data/`、`logs/`、环境变量、网络、壁钟时间、别的机器) ⇒
> 它必须被**显式注入**, 否则这条守卫的绿是**机器给的, 不是代码给的**。

**附注(为什么这类问题会越来越多)**: 本项目的运维预案本身就在写 `data/` 下的文件
(开关、登记、溯源)。这是**好事**, 但意味着
**"测试的隐含前提"与"运维的显式动作"共用同一个目录** ——
二者的冲突只会随运维成熟而**增加**, 不会减少。故这条纪律要现在就立。

**④ 是 ①/②/③ 之外的另一类, 也是唯一"测试本身没毛病"的一类**:
用例写得对、跑到了、前置也造出来了 —— 错的是它**据以判断的规格**。
它比 ① 更难发现: ① 的断言弱, 换个坏样本就露馅; ④ 的断言很强,
**只是锁在了一个错的前提上**, 喂坏样本也照样"正确地"失败/通过。

实例(2026-09-23, 真实事故): `datasource_gate.evaluate()` 里有一句
`n_now = cf["n"] + 1`, 注释是"**加上本次**这一次失败（账本里可能还没记）"。
两个用例据此写成「账本造 **2** 条失败 ⇒ 断言 `HALT`」——
阈值 `FAILS_TO_HALT` 明明是 **3**。它们没写错, 只是**接受了"2 条 +1 = 3"这个实现算术**。
而生产里 `run_daily` 记完账之后, 守护进程**又读同一天的产物再判一次**,
那次 `+1` 把**同一次失败数了两遍** ⇒ 实测账本只有 2 条却报 `[HALT×3]`
⇒ 次日 `run_daily` **跳过摄入与选股**(提前一天停手, 且不报错、不告警)。
**两个用例全程绿灯** —— 因为它们忠实地验证了那个错误的规格。

**判据(④ 的通用对策)**:

> **判据用"业务事实", 不用"实现算术"。**

同一件事的两种问法:
- ❌ 实现算术: 「2 条账本 + 1 次观测 = 3」→ 这只在"观测未入账"时才成立, 且**没人检查过这个前提**;
- ✅ 业务事实: 「阈值 3 = **3 次真实失败**」→ 不管代码怎么算, 这一条永远为真。

**可操作的检查**: 读到 `阈值 / 计数 / 上限` 类断言时, 问一句
「**这条断言里的数字, 是我从需求推出来的, 还是从实现反推出来的?**」
凡是"实现里刚好 +1 / 刚好减一 / 刚好两倍"才成立的, 都要回到需求重算一遍。
`+1`、`off-by-one`、单位换算(`手` vs `股`)是 ④ 的高发区 ——
它们都是"实现细节泄漏进规格"的典型形态。

#### ④b 边界腐烂: 按**标识**切片, 而标识已被改名

④b 与 ④ **并列**, 但坏的位置不同: ④ 坏在**规格**, ④b 坏在**定位**。

```python
j = src.find("### 四种", i)     # 该标题已被改名 ⇒ 返回 -1
block = src[i:j]                # src[i:-1] ⇒ 取到**几乎整篇**
```

**Python 切片对 `-1` 不报错** —— 这就是它整类问题的根:
`find` 的"没找到"用 `-1` 表示, 而 `-1` 在切片里是个**合法的负索引**,
于是"找不到边界"被静默翻译成"取到文末"。

**实例(2026-09-26, 真实事故)**: DISC-2 的详细章节标题由
`### 四种"测试看起来正常"…` 改为 `### 详细判据: 四种… + 三种…`,
而**三个用例仍按 `### 四种` 切片**:

| 受影响断言 | 方向 | 后果 |
|---|---|---|
| 「每列必须给出可执行的检查方法」 | 正向 | 变成在**全篇**找形态行 ⇒ 索引表之外也能命中 ⇒ 比设计**更松** |
| 「索引里不该有多列形态」 | **反向** | 切片被详细章节喂饱 ⇒ **恒真** |
| 「索引块 = i..j」 | —— | 边界不存在, 语义整体失效 |

**为什么它是 🔴 高**: ④b 的失效方向**几乎总是"断言变弱"** ——
报告更绿, 没有任何信号。这与 ④ 同族("全绿但规格是错的"),
区别是 ④ 的测试**在验证一条错的规定**, ④b 的测试**在验证一片错误的区域**。

**修法(两道闸门, 缺一不可)**:

> **1. 标识集中成常量** —— 不许多处各写一份字面量。
> 本次: `_DETAIL_HEADING = "### 详细判据"`, 三个用例共享它。
>
> **2. 加一条「边界确实存在」的闸门** —— 这一步才是关键:
>
> ```python
> assert src.count(_DETAIL_HEADING) == 1     # 恰好一次
> assert 0 < i < j                           # 先后次序成立(而非 -1)
> assert j - i < len(src) // 2               # 切片占幅合理
> ```
>
> **为什么必须有第 3 条**: 前两条只保证标识**存在**, 不保证切片**合理**;
> 而本题的失效形态恰恰是"边界不存在 ⇒ 切片异常巨大"。
> 占幅断言是唯一能自动发现"切歪了"的判据 —— **它把"-1 被当成合法索引"
> 这件事变成一个可失败的断言。**

**通用判据**:

> 凡按**标识**(标题 / 键名 / 标记串 / 分隔符)切片的代码, 都要问:
> 「**这个标识还在吗? 它唯一吗?**」
> 两个问题的答案都必须是**运行时断言**, 不能是"我记得它在"。

**同族先例**: 本仓已修过的「告警规则从未被加载」是同一形态的**运行时版本**
(相对路径导致读的是另一份文件, 而文件**存在**、也不报错)。
④b 是它的**测试版本**: 两份都"存在且合法", 但引用的那个不是被测的那个。

### ⑤ 归因在中间层丢失: 错误信息把排查者引向**错误方向**

前四种形态坏的是"**有没有发现**问题"; ⑤ 坏的是"**发现问题之后往哪儿查**"。
它比前四种更贵: 前四种最多让问题漏过去, ⑤ 会让人**朝反方向投入时间**。

**实例(2026-09-23, 真实事故)**:

症状是 `db_update` **12/12 张表全部失败且 rows=0**, 连续两天, 第三天会触发熔断。
回执里给出的信息是:

```
db_update: ok=false  tables: 12 张全部 {ok:false, rows:0}
note: "AKShare 在非交易时段 / 网络受限 / 接口变更时返回空数据;
       daily_bars 路径已由 free_stockdb_sync 兜底"
akshare_stats: {"last_status":"ok","last_err":"","network_errors":0,"empty_count":0}
```

**`note` 把方向指向了 akshare**(非交易时段/网络受限/接口变更),
于是排查从"akshare 链路为什么没产出"开始 —— 而真因是:

```
DuckDB 不可用 (FileNotFoundError), update_all 降级跳过写库:
  DuckDB 已退役/不存在: ...\data\legacy_stockdb.duckdb
```

**与 akshare、网络、接口变更全都无关** —— `_connect_write_retry()` 在任何网络
调用**之前**就抛错, `update_all` 走**提前返回**分支把 12 张表全标失败。

**真因在哪里丢的**: `update_all` 返回的每张表**都带着** `error` 字段:

```python
daily_bars: {"ok": False, "rows": 0,
             "error": "DuckDB 已退役/不可用, 表级写入降级跳过"}
```

而 `run_daily` 构造 `tables_dict` 时只投影了 `{"ok", "rows"}` ——
**`error` 在中间层被丢掉了**; 这条路径上步骤级 `error` 本来就不存在。
于是回执里只剩一句**与事实相反**的 `note`。

**注意它和"检查项静默消失"(DISC-2 主体)** 的区别:
那个是"这一项**没有被检查**", 这个是"检查了、也失败了、**原因也拿到了**, 但原因
在往下传的路上被丢了"。前者是**采集**缺失, 后者是**传递**缺失。

**判据(⑤ 的通用对策)**:

> **1. 每一层都保留 `error`, 不许"投影成摘要"时把原因丢掉。**
> 汇总层只该**增加**信息(加上下文/时间/来源), 不该**减少**信息。
> 只要有人在中间做了 `{k: {"ok": v["ok"], "rows": v["rows"]}}` 这种字段投影,
> 原因就有丢失的风险 —— **投影是 ⑤ 的高发点**。

> **2. 用"独立反证"确认真因, 不要相信现成的归因文本。**
> 本次定案靠的是 `akshare_stats.network_errors == 0 and empty_count == 0` ——
> **供应商自评说自己一次错都没出**, 从而反证"akshare 链路坏了"这个说法不成立。
> 一个数字能证伪一整段解释时, 优先信那个数字。

> **3. 错误的"规模"不作归因依据 —— 只作优先级依据。** (2026-09-25)
>
> 这是 ⑤ 里最容易被违反的一条, 因为"数一下有多大"看起来像是在做定量分析。
>
> **同一份数据里, 28 与 100 倍都出现过, 而它们的"大小"与"该不该管"完全无关**:
>
> | 实测差异 | 规模 | 当时的判断 | 依据是什么 |
> |---|---|---|---|
> | 引擎 vs 聚宽同一只同日成交量差 **28 股** | 极小 | **不算问题**(手→股的取整) | 手是整数单位, 换算必然截断 —— **机制**说得通 |
> | akshare 成交量差 **100.0001 倍** | 极大 | **必须管**(单位是手) | 比值是**常数**, 不是"每次不同" —— **结构**说得通 |
>
> 两者都不是靠"差了 28 所以没事 / 差了 100 倍所以有事"定的。
> **若反过来**: 那条 28 股的差异也可能是"这个源少算了不足一手的零头"这个真缺陷的**唯一线索**;
> 而 100 倍也可能只是某天的一次异常样本。**规模本身什么都不说明。**
>
> **为什么"规模"会骗人**: 它只回答"症状有多大", 而归因要回答"**成因是什么**" ——
> 这两件事之间**没有映射**。小差异可能源于根本性的口径错误(只是恰好样本小),
> 大差异也可能源于一次性的、已被解释的取整。用规模当依据, 等于用
> "这事看起来严重不严重"当依据。
>
> **该用什么代替规模**: 用**能不能用机制解释**, 以及**是不是稳定的结构**:
> - 28 股: 能用手→股的整数截断**逐笔算出来** ⇒ 机制成立 ⇒ 可接受;
> - 100 倍: 比值是 `100.0001` 这个**接近常数**的值 ⇒ 是单位换算而非随机误差 ⇒ 必须处理。
>
> **可操作做法**:
> 1. **先问"这个数差在哪一步"**, 再问"差多少" —— 顺序反了就会以规模定案;
> 2. 差异若能用**一条明确的机制**逐值复算出来, 就不是缺陷(并把该机制写进注释/守卫);
> 3. 差异若**同向且近似恒定**, 那是口径问题(单位/复权/市场), **再小也要处理**;
> 4. 差异若**忽大忽小无规律**, 那多半是噪声或个别坏数据 —— 但也**不能只看规模就放过**,
>    要落到具体标的上查一次。
>
> **实例(2026-09-25, 本仓)**: 全市场回填被守卫**整日拒绝**, 报 `bad_rows=12`。
> 规模极小(12 / 5212 = 0.23%), 若按"这么小应该没事"跳过, 就会**放行一个真的 12 行缺口**;
> 若按"有 12 行不合规所以整日废掉", 又会**把 5200 只有效行一起丢掉**。
> 两个方向都是拿规模当依据。正确做法是**查这 12 行是什么** ——
> 结果全部 `tradestatus=0`(停牌), 属正常状态 ⇒ 剔掉这 12 行、保留 5200 行。
> **规模给了两次相反的暗示, 而两次都错了。**

**同类先例**(本仓已登记的 `write_with_version` 异常被吞)本质相同:
**信息在传递链的某一环丢失**。区别只在丢的是异常还是字段。

**⑤ 的价值会随时间增长**: 前四种形态修一次就少一类, 而"中间层丢信息"会随着
链路变长而**自然增多** —— 每一层新增的汇总/投影都是一次新的丢失机会。

#### ⑤ 的元特征: 它与「认真程度」无关 (2026-09-25)

这是本纪律最反直觉、也最该记住的一条。**同一批工作里, 我在新写的约 200 行代码中
犯了三次 ⑤** —— 而我当时正在**修别人**的 ⑤:

| 错误 | 形态 | 为什么 |
|---|---|---|
| stdout 被截断(339 项清单) | ⑤ 变体 | 结论字段全丢 ⇒ 无法判断它为何失败 |
| `normalize()` 返回 `(df, meta)` 元组, 我当裸 DataFrame 用 | ⑤ 直接 | guard 抛 `AttributeError` ⇒ 被包装成 `guard_error`, 真因不可见 |
| `validate_daily_bars` 返回 `{ok, bad_rows, checks, sample}`, **没有 `reasons`** | ⑤ 直接 | 我取 `reasons` ⇒ 留下 `{"ok":false,"reasons":[]}`: **拒了, 但没说为什么** |
| `pa.Table.from_pandas(frame)` 少了 `ts` 列 | ⑤ 直接 | 承接方(schema)要 `ts not null`, 我给的表里没有 |

**四条全是同一件事: 「承接方认的字段」与「我给的字段」不一致。**

结论不是"要更小心" —— 那是没用的建议。结论是:

> **判据要从「检查自己有没有出错」改成「检查承接方到底认哪个字段」。**

前者依赖注意力, 后者依赖**一次对照**; 注意力会耗尽, 对照不会。可操作做法:

1. **读承接方的代码/文档, 抄下它认的字段名与类型**(不是"大概叫什么");
2. **看它的返回**, 不要照自己的假设取名 —— `validate_daily_bars` 返回 `checks`,
   我却写了 `reasons`, 而**它不会报错**, 只会安静地给我一个空列表;
3. **问一句「这个失败信息里, 真正能定位问题的字段是哪一个?」** 若答案是"不知道",
   那就是 ⑤ 已经在发生;
4. **别把结论交给会截断的管道**: 那次 stdout 被 339 项清单截掉, 导致我
   **多跑了两次 30 分钟的全市场取数**。结论要落盘成文件。

**为什么它比前四种更难自察**: ①③④ 的失败会以"测试红了/断言错了"的形式**主动**找你;
⑤ 的失败**看起来一切正常** —— 代码跑通了、返回了字典、没抛异常, 只是那个字典里
**没有你要的信息**。它不制造错误, 它制造**空白**, 而空白最容易被当成"没问题"。


### ⑥ 降级过程无告警: 系统**正确地**降级, 却没人知道

⑥ 与前面五种都不同, 值得单独说清**它不是什么**:

- 它不是①(断言弱): 系统**确实检测到了**问题;
- 它不是"静默失败": 系统**没有吞掉**任何东西, 它如实记录了, 也如实降级了;
- 它更不是"检查项消失": 检查在跑、结论也对。

**它的形态是: 从"健康"到"停手"之间有几个档, 而中间档位没有任何告警负责。**
系统**完全正确地**沿着这些档位往下滑, 每一档都比上一档更糟, 而**人不知道** ——
直到滑到底、触发那条唯一的 critical 告警为止。此时根因往往已无从查证:
现场被后续的重试/覆盖冲掉, 能查的只剩"它停了"。

**实例(2026-09-25, 真实事故)**:

厂商引擎停在 2026-09-22, 应到 09-24 ⇒ 落后 **2 个交易日**。系统的每一步都对:

| 层 | 行为 | 对不对 |
|---|---|---|
| `target_plan.data_lag_days` | 逐日记为 1 -> 2 | ✅ 如实 |
| `target_plan.section_as_of` | 两天都是 2026-09-22 | ✅ 如实 |
| 门禁 | `DEGRADED`, `allow=True`(落后 2 < 硬阈值 3) | ✅ 符合设计 |
| 引擎探针 | `freshness.ok=False`, `lag=2` | ✅ 忠实 |
| 选股 | **仍照常跑**(用旧截面) | ✅ 符合设计 |

**五处全对, 零条告警。** 而当时拥有的两条规则分别盖在两端:

| 规则 | 覆盖的档位 |
|---|---|
| `TableStaleDaily` | 只在 **5 个自然日**后(实测 `daily_bars` 才 3.08 天) |
| `DataSourceHalt` | 只在 `allow == 0`(即**已经停手**)时 |

⇒ `落后 1 ~ 3 个交易日` 这**整段"正在降级"的窗口里, 没有任何告警**。

**为什么这比"静默失败"更难发现**: 静默失败是**该报的没报**;
⑥ 是**该报的都报在别的档位上**。你去看告警清单, 会看到两条规则、
它们各自都"工作正常"、各自都"没到阈值"—— 没有任何东西看起来是坏的。
**缺的不是某条规则的功能, 而是覆盖本身**: 没人问过
「这套分档里, 哪几档是没人管的?」

**判据(⑥ 的通用对策)**:

> **1. 把分档列出来, 逐档问"这一档谁负责叫"。**
> 对每个"有中间状态"的机制(门禁的 OK/DEGRADED/HALT、数据的新鲜/延迟/停更、
> 组件的正常/降级/停摆), 画一条档位轴, 标注每档由哪条告警覆盖。
> **两档之间有缝, 就是⑥。**

> **2. 告警阈值要定在"该有人开始看"的档位, 而不是"已经出事"的档位。**
> 只在最后一档报警 = 把"预警"和"事后通知"混为一谈 ——
> 而人在最后一档能做的往往只剩"手工恢复", 已经失去了"在恶化前干预"的机会。

> **3. 量化值要暴露出来, 不要只暴露布尔值。**
> 本次能做对全靠 `lag_trading_days` 这个**整数** ——
> 而 `freshness_ok` 是布尔的, 布尔值无法划出中间档位。
> **一个布尔只能表达两档, 而现实往往有三档以上。**

**本次的落地**: 补 `astock_engine_lag_days` 指标 + `EngineDataLag`
(`> 1` 个**交易日**, warning), 并同时补 `EngineDataLagUnreadable`
(否则新规则自己失效时又会变成一次⑥)。阈值取 1 而非 0: 落后 1 天属 A 股正常的
盘后发布延迟, 报了就是噪声 —— 而**噪声告警会训练人忽略频道**, 那是另一种形态的⑥。

#### ⑥ 的补充实例: **守卫自指涉** —— 守卫自己成了破坏源 (2026-09-25)

与「守卫依赖缺失」并列, 但形态不同。**刻意把"自指涉"分成良性与恶性两档** ——
因为它们的后果差一个数量级, 而**恶性那一档正是 ① 假信心测试的制造过程**:

| 形态 | 现象 | 后果 |
|---|---|---|
| **守卫依赖缺失** | 守卫**没跑**(依赖不在/环境不对) | 它保护的路径**无人看守** |
| **守卫自指涉(良性)** | 守卫跑了, **报的是它自己** | **本次报错 ⇒ 立刻可见, 可发现** |
| **守卫自指涉(恶性)** | 守卫跑了, **永远通过** | **退化成 ① 假信心测试, 且更隐蔽** |

**恶性形态为何更隐蔽**: 它**看起来真的在检查** —— 有 AST、有扫描、有 `total > 0`,
报告写着"全部合格"。而真相是它的模式串**恰好只匹配它自己**(或不匹配任何真实目标),
于是永远通过。与 ① 的区别: ① 是"断言太弱", 这条是"**压根没检查到目标**"。

**实例(实测)**: 2026-09-25 我新加了一条静态守卫
`TestEveryYamlUsingTestIsMarked`, 用来扫描"用了 yaml 的用例有没有挂 `@_needs_yaml`"。
它**第一次运行就报了它自己**:

```
AssertionError: 以下用例用了 yaml 但没挂 @_needs_yaml ...
  assert not ['test_discipline_doc.py::TestEveryYamlUsingTestIsMarked::test_no_yaml_using_case_misses_the_marker']
```

**根因**: 该守卫的**提示文本里**含 `yaml.safe_load` 这个模式串, 而
`ast.get_source_segment` 返回的片段**包含 docstring** ⇒ 它把自己的说明文字
当成了"被检查的代码"。**即"用来描述规则的话"被"规则的判据"当成了输入。**

**为什么这次是良性的、但同类问题可能很恶性**:

- 良性: 它**报错而不是静默通过** —— 立刻可见, 改掉即可(本次按类名过滤);
- 恶性(必须防): 若某守卫的模式串**恰好只匹配它自己**、而真实目标一个都不匹配,
  它会**永远通过**并报告"全部合格" —— 那就从"守卫自指涉"退化成
  **① 假信心测试**, 且比①更隐蔽: 它看起来**真的在检查**(有 AST、有扫描、有 `total > 0`)。

> **⚠️ 「扫描量下限」是防恶性形态的**唯一闸门**。**
> 本次写的是 `assert total >= 13` —— 若将来判据被写窄(只匹配到两三个),
> **这条会失败**, 而不是安静地"全部合格"。
> **没有它, 良性形态随时可能退化成恶性形态而无人察觉** ——
> 而"无人察觉"正是这一整节要防的东西。

**判据(③ 与 ⑥ 的交叉, 可作为通用检查)**:

> **1. 守卫的判据里不要出现"用来解释守卫的话"。**
> 具体做法: 把模式串与提示文本**分开** —— 判据用变量/常量, 提示用自然语言描述,
> 不要让同一段文字既当"规则说明"又当"匹配目标"。

> **2. 守卫必须**声明它排除了什么**, 且排除范围要能在断言里看见。**
> 本次的写法: 按**类名**排除本守卫(不是按文件路径), 并在断言文本里写明
> "「本守卫自身除外」" —— 过滤是**声明的输入**, 不是偷偷跳过检查。

> **3. 加一条"扫描量下限"断言, 防止判据意外变窄。**
> 本次: `assert total >= 13` —— 若将来判据写窄了(只匹配到两三个),
> 这条会失败, 而不是安静地"全部合格"。**这是防 ⑥ 退化成 ① 的那道闸。**

**同类先例**: `test_no_single_threshold_for_all_tables` 那条守卫
(禁止 staleness 一刀切)在 2026-09-25 把日报类拆成三档后仍须通过 ——
它的价值恰好在于**"分档可以更多, 但不能退回单一阈值"**这个不变量,
而不是"必须恰好两条规则"。**守卫要守不变量, 不要守实现细节** ——
否则每次正常演进都会撞它, 最后被人"顺手"放宽到毫无作用。

#### 守卫自指涉的**第三种形态**: 判据命中"关于判据的数据" (2026-09-26)

前两种是「判据命中守卫**自己的源码**」; 第三种是「判据命中一个**测试样本字符串**」——
后者不是代码, 而是**用来喂给判据的数据**, 但它在 AST 里长得和代码一样。

**实例**: 2026-09-26 我加了一条静态守卫 `TestNoTestCallsAnUndefinedHelper`
(查"用例调用了不存在的 helper"), 它带**反向验证**样本, 样本串里写了
`rules = _load_rules()`。而 `TestEveryYamlUsingTestIsMarked` 的判据里有一条
`"_load_rules(" in body` —— 于是那条守卫把**我的样本**报成了"用 yaml 却没挂装饰器"。

**与良性自指涉的同一个根因**: `ast.get_source_segment` 返回的片段**包含字符串字面量**。
凡"按源码文本判断语义"的守卫, 都会把**注释、docstring、样本串**当成代码。

| 自指涉形态 | 命中的是什么 | 处置 |
|---|---|---|
| 良性(09-25) | 守卫**自己的 docstring/提示文本** | 按类名排除本守卫 |
| **第三种(09-26)** | 另一守卫的**测试样本字符串** | 按类名排除那个守卫, 并写明理由 |

**更一般的判据(推荐记牢)**:

> **按源码文本模式的守卫, 必须显式声明它排除了哪些"文本容器"。**
> 因为注释、docstring、测试样本、多行字符串**都与真代码同形**。
> 排除项要写**理由**, 不能只说"排除 X" —— 否则后人分不清这是
> "已知的判据副作用"还是"为了让它变绿而加的例外"(后者是守卫退化的开始)。

#### 一条**空守卫**的完整病历: 它连负样本都抓不到 (2026-09-26)

同一天写上面那条守卫时, 我**连写了三版**, 前两版都不能用。这一节完整保留,
因为"**空守卫**"比"没有守卫"危险得多 —— 它占据着"已覆盖"的位置。

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | 收集 `def`/参数名再比对 | **大量假阳性**: 内置 `__import__`、函数内局部定义的类都被报成"未定义" |
| v2 | `symtable` 遍历子表 | 仍有假阳性: `seen`/`called` 这类**在别的作用域里赋值**的名字被误报 |
| v3 | 只看 `Call` + "任何作用域都没绑过此名" + 跳过首字母小写 | **0 假阳性**(全仓 90 个测试文件), 且能抓到原缺陷 |

**v2 为什么也错**: 我只看了"本函数的符号表", 而 `seen` 是在**别的函数**里赋的值
⇒ 判据比语言语义**更窄** ⇒ 误报。**会误报的守卫等于没有** ——
它会被"顺手"放宽或删掉(印证上面「守卫要守不变量」那一节)。

**最贵的一课(v1 的自我打脸)**: v1 的反向样本我用的是 `_LoadRules()`,
而过滤器写成 `if not nm[:1].isupper(): continue` —— `"_"[:1].isupper()` 是 **False**
⇒ **连反向样本自己都被跳过**。于是"负样本没报警"被我读成"负样本通过"。

> **⚠️ 一个连负样本都抓不到的守卫, 会显示为全绿。**
> 故「负样本必须被抓到」这条断言**不是装饰**, 是这类守卫的**唯一存在性证明**。
> 通用写法: **每条"静态扫描"类守卫都要带一个"它必须报警"的样本** ——
> 只有"不该报的没报"是不够的(空守卫同样满足那一条)。
>
> **推广到"守卫的负样本必须能触发守卫"**(2026-09-26 用户建议单列):
> 这不是测试技巧, 而是**存在性证明**。判据是:
> 「**把被判据禁止的东西造出来, 这条守卫会红吗?**」
> 不会红 ⇒ 它没有在守任何东西。做法: 给守卫配一个**确定违规**的样本
> (本例: 直接喂 `_load_helper()` 这行样本, 断言 `_scan` 必须返回它)。
> **注意样本本身也可能被判据过滤掉**(本例 v1 就是如此) ——
> 故样本要**断言它真的被抓到**, 而不是只断言"扫描通过"。


### ⑦ 证据无判别力: 拿一条"两个假设都成立"的证据当成确认

⑦ 与前面六种都不同, 先说清**它不是什么**:

- 不是 ①(断言弱): 我拿到的那条证据**是真的**, 断言也没写错;
- 不是 ②(skip): 证据**确实被执行、确实为真**;
- 不是 ④(规格错): 规格没错, 错的是**从证据到结论的那一跳**;
- 不是 ⑤(归因丢失): 信息没有在中间层丢失, 它**完整地**到了我这里;
- 也不是 ⑥(降级无告警): 这里**没有发生降级**, 一切"正常"。
- 更不是"我没查" —— 我**查了**, 而且查到的数字全对。

**它的形态是: 证据为真, 但它对两个<u>互斥</u>假设<u>都成立</u>, 因而没有判别力。**

#### 实例(2026-09-26, 代价很高)

我把告警 `DrlEnvMissing` 登记成「**已知结构性误报**」, 理由是
"探针探的解释器 ≠ 训练用的解释器"。我拿的"证据"是**真的**:

```
data/drl/20260924/drl_train_heartbeat.json
  = {phase: "done", ok: true, total_timesteps: 800}      # 训练成功
```

**但这条证据同时兼容两个互斥假设**:

| 假设 | 训练成功? | 探针报"缺依赖"? | 与心跳一致? |
|---|---|---|---|
| **(a)** 探针探的是**另一个**解释器 | ✅ | ✅ 两者并存 | ✅ |
| **(b)** 探针探的**就是**训练那个解释器, 环境本来就齐备 | ✅ | ❌ 探针应报 ok | ✅ |

**我只看了训练心跳** —— 而它与 (a)(b) **都一致** ⇒ 它**没有判别力**。
我却把它当成了对 (a) 的确认。

**真正的判别观测**是「那个 `PY` 从哪来」, 一查就定了:

| 查证点 | 事实 |
|---|---|
| `src/daemon.py:35-40` | `PY = sys.executable`, 若 `TRAE_PYTHON` 存在则覆盖 —— **唯一来源** |
| `src/daemon.py:567-570` | metrics_server 用**同一个** `PY` 启动 |
| `run_daily` | 同样由该守护以该 `PY` 启动 ⇒ **所有子进程天然同源** |
| `scripts/start_daemon.ps1` | 默认用 **`.venv310`**; 而 `P0-DRLDEP` **已于 09-20 修复**, 四项齐备 |

⇒ 结论是 (b): **探针与训练共用同一个解释器, 环境四项齐备, 该规则从未真正故障**。
实测 `astock_drl_env_ok=1`、规则 `inactive`、
`daily_summary` 的 `drl_degrade.probe.missing=[]`、`drl_train.ok=true`(产出 `model.zip`)。

#### 后果: 把错误判断**写进注释**, 让后来的人也照错

这是 ⑦ 与其它形态**最不同**的地方 —— **它污染的不是过程, 是<u>结论</u>。**

一个标着"已知误报"的**真**告警, **比没有告警更坏**:

| 情形 | 值班人看到 | 他会怎么做 |
|---|---|---|
| 没有这条告警 | "这个域没人管" | **去找**是否有问题 |
| 告警在, 但被文字解释掉 | "已知误报, 见 P0-DRLDEP" | **照着注释忽略它** |

**这是 ⑥ 的反向形态**: ⑥ 是"降级无告警"; ⑦ 是「**告警在, 但被文字解释掉了**」。
⑦ 的输出会进入**注释、登记册、复盘记录** —— 于是它不仅骗过当下,
还会**持续地**骗过每一个后来读它的人(本次若不做更正, 将来真缺依赖时必然被忽略)。

#### 为什么它特别难自查

因为**它伪装成"我已经查过了"** —— 而这是最不该被质疑的状态:

- 我有证据(心跳), 且**证据为真**;
- 我做了推理(探针≠训练), 且**推理形式正确**;
- 我还做了交叉核对(心跳 vs 探针报的值) —— **但这对核对没有判别力**。

⇒ 整个过程**每一步都"像"严谨的**, 唯独缺了那一次**能分开假设的观测**。

#### 判据(⑦ 的通用对策)

> **拿到一条证据时先问: 「如果反过来才是真的, 这条证据会不一样吗?」**
>
> · 会不一样 ⇒ 它有判别力, 可以作为确认;
> · **不会不一样 ⇒ 它只是"与假设相容", 不构成确认。**
>   此时必须继续找那个**能把两个假设分开**的观测。

**落地习惯(建议)**: 在把任何判断写进**注释 / 登记册 / 文档**之前
(即"要留给后人看"的地方), 强制过一次这个问句。
理由是 ⑦ 的代价**随时间累积**: 写错一次, 后面每个人都会继承这个错误。

**与 ⑤ 的分工**: ⑤ 问「**这条错误信息有没有独立数字能证伪它?**」(排查方向),
⑦ 问「**这条<u>正确</u>的证据能不能区分假设?**」(确认效力)。
⑤ 的输入是错的, ⑦ 的输入是对的 —— **后者更难发现, 因为没有任何东西看起来不对。**

#### ⑦ 的第二个判据: 「**这个判据, 能区分对错吗?**」(2026-09-26)

上面那个问句管的是**证据**; 这一个管的是**判据本身** ——
写一条断言/判据时, 问:

> **「这条判据, 在'做对了'与'做错了'两种情况下, 结果会不一样吗?」**
>
> · 会不一样 ⇒ 它有判别力, 留着;
> · **两种情况下结果相同 ⇒ 它是错的判据** —— 不是"不够严", 而是**根本不测那件事**。

**反例(我自己刚写的, 当场删掉)**: 为验证「叙述区识别得对不对」, 我写了

```python
assert len(runs) <= 4, "叙述区被切成了 N 段, 疑似识别过宽"   # ❌ 错的判据
```

**它错在哪**: 本文档的引用块(`>`)本来就**散落在全文各处**, 正常状态下
实测是 **34 段** —— 即"做对了"也会失败;"做错了"(识别过头成一大段)反而**段数变少**,
**会通过**。⇒ 它与被判定的那件事**方向相反**, 是个纯噪声判据(会误报, 且漏报)。

**换成的判据**: `sum(flags) < len(lines) * 0.5`(**叙述区占幅 < 半篇**)。
理由: 本次真实 bug 是「识别过头 ⇒ 叙述区被算到几千行」, **占幅会立刻超一半**;
而正常状态下引用块虽多, 总占比很小。⇒ 两种情况结果**确实不同**。

| 判据 | 做对了 | 做错了(识别过头) | 能区分? |
|---|---|---|---|
| ❌ 段数 ≤ 4 | 34 段 ⇒ **失败** | 1 大段 ⇒ **通过** | **不能, 且方向相反** |
| ✅ 占幅 < 半篇 | 占比小 ⇒ 通过 | 占几千行 ⇒ **失败** | ✅ 能 |

**为什么这条要单独立**(与上面那条的分工):

| 问句 | 管的是 | 失效表现 |
|---|---|---|
| 「反过来才是真的, 证据会不一样吗?」 | **证据的效力** | 拿无判别力的证据当确认(⑦ 本体) |
| 「这个判据能区分对错吗?」 | **判据的效力** | 写了一条"两种情况同结果"的断言 |

两者同源(都在问"能不能分开两种情况"), 但**一个是读证据, 一个是写判据**。
后者更常见于**新写的守卫**: 因为写的时候满脑子是"要检查 X",
于是随手挑了一个**看起来与 X 相关**的量(段数), 而没问它是否**真的随 X 变化**。

> **判据(自查动作)**: 写完一条守卫, **先把"做错"的情形在脑子里跑一遍** ——
> 问「**这种情况下, 我这条断言会红吗?**」
> 若答案是"不会红"或"我不确定", 那这条守卫是**装饰**,
> 必须换成一个**已知会在那种情形下变化**的量。
> (与「负样本必须能触发守卫」是同一件事的两个说法:
> 那条要求你**真的喂**一个负样本; 这条要求你**在写的时候就问**。)

#### ⑦ 的第三个判据: 「**结论相同、来由不同处, 必须连判据一起记**」(2026-09-26)

> **若同一个结论(状态/动作/返回值)有两个或以上不同来由,
> 记录时必须把<u>判据</u>一起记下来, 不能只记结论。**

**为什么**: 只记结论 ⇒ 事后**无法重建**当时的局面。
而"两个来由"往往对应**相反的运维动作** —— 记不清就会照错的那个去处理。

**实例(2026-09-26, 09-28 回填实验的准备工作)**: `backfill_trigger` 的
`action` 有三种取值, 其中 `no_gap`(不触发)**有两个来由**:

| `A_engine_gap` | `B_h5i_gap` | action | 真实含义 |
|---|---|---|---|
| `false` | 任意 | `no_gap` | **厂商已恢复** ⇒ 没有"厂商缺席的日子"要补 |
| `true` | `false` | `no_gap` | **厂商未恢复, 但 h5i 已补齐** ⇒ 重复回填无意义 |
| `true` | `true` | **`trigger`** | 真正要回填的缺口 |

前两行**打印出来完全一样**(都是 `no_gap`), 但含义相反:
一个是"厂商好了, 系统什么都不用做", 另一个是"厂商还坏着, 只是存储恰好不缺"。
**若记录里只有 `action`, 一周后根本分不清当时是哪种局面** ——
而 09-28 那场自然实验要回答的正是这个问题。

**处置**: 已在 `docs/stockdb-source-status.md` §6.13 把
**`criteria` 两值列为检查单的强制第 0 项**, §6.14 的观测记录也按此补记。

**与 ⑤ 的关系(用户指出: 同族, 但更一般化)**:

| | ⑤ | 本条 |
|---|---|---|
| 管的是 | **排查方向**: 错误信息把排查者引向错误方向 | **记录完整性**: 结论被记下了, 判据丢了 |
| 典型症状 | 越认真读越可能走错方向 | 记录看起来齐全, 但**事后重建不了** |
| 对策粒度 | 「保留**每层**的 `error` 字段」 | 「凡**结论相同、来由不同**处, 连判据一起记」 |

⇒ ⑤ 是本条在**错误传递**场景下的特例: 它要求的"保留每层 error",
本质就是"不要只留最终那个 `ok`"。**本条把它推广到所有多来由的结论**,
不论那个结论是错误信息、状态码、还是动作名。

**判据(写法)**: 记一条结论时问
「**这个结论还有别的来由吗? 若只看我记下的东西, 别人能区分是哪一个吗?**」
答不出 ⇒ 把判据一起记。



### 关于「已提交 vs 已推送」: 两种状态必须可区分

上表第 6 条同理 —— 它不是"忘了推", 而是**没有机制提醒**:

| 状态 | `git status` | `_tools/push_state.py` |
|---|---|---|
| 已推送 | clean | `ahead=0` |
| **有未提交更改** | **看得到** | `ahead=0`(**不报**) |
| **已提交未推送** | **看不到** | **`ahead=N` + 提交列表** |

⇒ 两者**互补, 不重复**(已用实验确认, 见 `tests/test_push_state.py`)。
故 `push_state.check_push_state()` 归入**本纪律**, 而不是 DISC-4。

### 原则

1. **报告上"没有这一项"与"这一项没问题"必须可区分**。缺失的检查项要**显式**列出,
   不能靠"没报错"表示健康。
2. **采集失败 ≠ 健康**。`gather()` 取不到结论时要给出 `error` 字段并抬高状态
   (如 `freshness_undeterminable` / `DataSourceGateUnreadable`), **不得**默认放行。
3. **"没有告警"与"没有在监控"必须可区分**。账本为空是 `UNKNOWN`(监控未生效),
   不是 `OK` —— 这正是死手开关自己的立场(`verdict` 的 UNKNOWN 档不取 OK)。
4. **判据要能自证有效**: 每条"守卫/校验"都应有**反证用例**(喂一个坏样本, 必须失败),
   否则它可能形同虚设。

### 执行机制

- `health_state.assemble()`: `"deadman" in snap` 与 `dm is None` **分开处理**
  (前者是向后兼容的"没这一项", 后者是采集异常, 必须说出来);
- `datasource_gate.classify_engine`: 日历强度非 `official` ⇒
  `freshness_undeterminable`(**不可判定 != 健康**);
- `metrics_server`: `*_read_ok` 系列 gauge —— **读数失败显式暴露**, 不让旧值冒充健康;
- `tests/test_subprocess_decode_contract.py`: 把"静默 None"变成**提交时**就红的错误。

## DISC-3: 加速层**不得改变语义**

**状态**: 已固化(2026-09-22)。**执行机制**: 逐字段等价守卫。

### 事实依据

2026-09-22 优化选股性能时, 我在批量快照路径里"顺手多给了一个字段"
`liab_ratio` —— 而逐条路径**刻意不注入**它(duck 原实现恒 None, 为迁移前后
逐位一致)。多给一个字段就**改变了 `governance_score` 的输入**。

同批还有两处必须锁住:
- **前视风险**: 批量快照装的是"每个 symbol **最新一行**"(今天口径) ——
  历史回测若命中它, 就是把今天的财报喂给过去的选股;
- **索引路径 vs 布尔路径**: 为提速把 `g[g["symbol"]==sym]` 换成 symbol 索引,
  必须**逐行等价**。

### 原则

1. **性能优化只许改"怎么算", 不许改"算出什么"**。
2. 每条优化都必须有 **"与非优化路径逐字段等价"** 的守卫 ——
   且比对要 **NaN-aware**(含 NaN 的 dict 永不自等, 直接 `==` 会把"完全一致"
   误报成差异; 实测白查了一轮)。
3. **加速路径要有回退**: 索引/快照缺失时应**退回原路径**, 而不是报错或算错。
4. **不得顺手扩字段**: 想加字段就单独提, 不要夹在性能改动里。

### 执行机制

`tests/test_h5i_accel_equivalence.py`(8 例): 前视冻结(`_LATEST_SNAP_FROZEN`,
`_select_hist` 主动置位) + 批量快照与逐条 SQL 逐字段等价 + 索引路径与布尔筛选逐行等价;
且有 `test_optimized_accessor_is_not_named_and_shamed`(已优化好的存取**不再被点名** ——
优化完还被点名会训练人忽略报告)。

## DISC-4: 生成含大段中文的代码时, **先校验再落盘**

**状态**: 已固化(2026-09-22)。**执行机制**: `_tools/safe_write.py`。

### 事实依据

本会话**连续五次**栽在同一处: 在中文串里手写半角引号 `"…"`, 把 Python 字符串
字面量**提前截断**。`ast.parse` 每次都在**运行前**拦住了它 —— 但拦住之后我仍然是
**手改一处、再跑、再报下一处**, 因为:

> **报错行通常不是肇事行** —— 截断后解析器要往后找闭合, 报错位置常落在不相干的下一行。

**元教训: 守卫能拦住错误, 但拦不住低效的修复循环。**

### 原则

1. **把校验移进生成过程**: 内容拼好 -> `ast.parse` -> **通过才落盘**。
   一次收敛, 而不是 N 轮往返。
2. **语法不过时不得落盘** —— 不像"先写再修": 那会留下一个**坏文件**,
   而坏文件可能被别的进程导入或执行。
3. **内层引号一律用 `「」`**(中文全角), 不让半角引号出现在中文串里。
4. **报错信息要指向真因**: 工具必须提示"报错行常不是肇事行, 多半是前面某个字符串
   被中文半角引号截断", 而不是只丢一句 `invalid syntax`。

### 执行机制

| 机制 | 位置 | 管什么 |
|---|---|---|
| `write_python(path, source)` | `_tools/safe_write.py` | **生成**时: 先 `ast.parse`, 通过才落盘 |
| `validate_python(source)` | 同上 | 带上下文与真因提示的校验 |
| **`fix_text(src)` / `fix_file(path)`** | **`_tools/fix_cjk_quotes.py`** | **修复**时: 自动把中文串内嵌的半角引号改成 `「」`, 反复直到 `ast.parse` 通过 |
| CLI: `python _tools/fix_cjk_quotes.py <file.py>` | 同上 | 编辑既有文件后一键收敛 |
| CLI: `python _tools/safe_write.py <file.py>` | 同上 | 只校验不改 |
| **全仓编译守卫**(提交时) | `tests/test_python_syntax_guard.py` | 兜底: 任何 .py 语法错误都会在提交时红 |

**为什么必须有"修复端"**(本会话的追加教训):
`safe_write` 解决的是**生成**场景。但我**编辑既有文件**时又栽了两次 ——
因为校验端只能告诉你"错了", 而**报错行通常不是肇事行**, 于是仍然是
"手改一处、再跑、再报下一处"。
补上修复端后, 那个 8 轮的手工循环变成**一条命令**(实测: 本会话第 8 次踩坑时,
`fix_cjk_quotes.py tests/test_push_state.py` 一次修好并测试全绿)。

> **判据(为什么自动替换是安全的)**: 形如 `..."中文"中文"...` 的位置上, 那对引号
> **不可能**是合法的字符串界定符 —— 若它是界定符, 其后紧跟的中文会变成裸标识符而报错。
> 故"紧贴 CJK 的引号对"必然是内层引号, 替换无歧义。
> 且修复端**只动 `ast.parse` 报错的那一行**, 本就正确的代码一行都不碰(有测试锁住)。

> **职责边界**: "已提交但未推送"的检查**不在**本纪律 —— 它是 DISC-2, 且已独立成
> `_tools/push_state.py`(原先误放在 `safe_write.py` 里, 会让该模块职责糊掉:
> "代码生成校验"的工具里塞一个 git 检查, 下一个人不会去那里找它)。
> **一个模块一个职责。**
