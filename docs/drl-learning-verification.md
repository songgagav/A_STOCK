## 〇、两处前提必须纠正

1. **「硬边界约束（你已做 [0.10, 0.39]）」—— 已确认系记忆错误，并已按输出语义重新判定。**

   用户 2026-09-19 回溯确认：`[0.10, 0.39]` 来自更早对话中的**假设性讨论**，被当成了"已实现"。
   全仓 grep（`\b0\.39\b|weight_bound|WEIGHT_BOUND|\[0\.10`）在 `src/` 与 `scripts/` **零命中**，该结论成立。

   **按用户判定表重新定义**（取决于 DRL 输出语义）：

   | 边界类型 | 当前状态 | 是否应该存在 |
   |---|---|---|
   | 单票权重边界（6.0%~11.5%） | ✅ 已实现（`TARGET_WEIGHT.min_mult/max_mult = 0.60/1.15`） | 合理 |
   | **因子权重边界** | ❌ **不存在** | **需要**（见下） |

   **实测 DRL 输出语义 = 因子权重**（这是判定的关键，已实测）：
   - `train_meta.base_weights / prior_weights / final_weights` 都是 **6 元素 dict**，
     键为 `signal / trend / govern / liquidity / vol / mom_rev` —— 即**因子权重**；
   - 最新样本（20260905）`final_weights` =
     `{liquidity 0.3254, mom_rev 0.2626, signal 0.1823, trend 0.1073, govern 0.0995, vol 0.0228}`；
   - 再由 `target_plan.method = "drl_final_weights x v_universe_snapshot"` 算出**股票** top_n。

   ⇒ 依用户规则「若 DRL 输出因子权重，则需要独立的因子权重约束」：**需要，且当前不存在**。
   实测因子权重跨度 **0.0228~0.3254（13.6 倍差）**，无任何硬边界。

   > 附带观察：用户记错的 `[0.10, 0.39]` **很可能原本就是打算用于因子权重的** ——
   > 实测跨度恰好横跨该区间。若如此，该区间可作为因子权重边界的候选起点。

2. **DRL 并非独立调度阶段。**
   设计把 DRL 排在 19:00–21:00、独立于数据拉取与因子计算。实际：
   `daemon.py` 注释写明「**run_daily 整条管道含数据拉取+模型训练(DRL/vnpy)**」，
   且 `--maint` 在 **15:05~22:00 窗口每天跑一次**；收盘选股本身已从 15:05 **后移到 19:10**
   （因数据商收盘后 1–4h 才更新，15:45/16:40 由 `data_update_daemon` 分窗口补数）。
   ⇒ 现状是「**一条大管道**」，DRL 与选股共用边界，**没有独立的 DRL 检查点/闸门**。
   设计的时序意图（数据就绪之后、次日信号之前）大体满足，但**可观测性不满足**。

## 五、降级链：设计 → **已实现（DRL-4，2026-09-19）**

设计：
```
正常学习（增量训练）
  → 学习失败/验证不通过 → 保留旧模型，告警
    → 旧模型损坏 → 回退到上一个有效版本
      → 无有效版本 → 暂停交易，人工介入
```

### 5.1 实现（`src/drl_degrade.py`，轻量，不依赖 torch/gymnasium/stable_baselines3）

选轻量模块是**为了 CI**：`drl_train.py` 导入即拉 torch，若把降级链写进去，
「不装 torch 的 CI core job」连测试收集都会失败（同一理由见 DRL-7 的 `drl_drift.py`）。

| 级别 | 名称 | 触发条件（**全为结构性，不含统计阈值**） | 处置 | 告警 |
|---|---|---|---|---|
| `L0` | 正常 | 训练成功且 `final_weights` 非空 | 部署新模型；若上一轮处于降级，**记一条恢复事件** | INFO |
| `L1` | 保留旧模型 | `train_ok=False`（含数据不足、未捕获异常）或训练无有效权重 | 继续用当前模型，**不部署新模型**（指针 day 不动） | WARNING |
| `L2` | 回退上一有效版本 | 当前模型结构性不可用 | 扫描最近一个**实盘且可用**的版本并改指指针 | ERROR |
| `L3` | 暂停交易 | 无任何有效版本 | **不生成当日 plan**（`blocked_by_degrade=True`） | CRITICAL |

- **落点**：`drl_train` 中 `drl_degrade.resolve()` 调用在 `_build_target_plan()` **之前**
  ⇒ L3 才能真正阻断当日 plan，而不是"事后告警但计划已生成"。
- **可逆**（设计要点①）：指针 `data/drl/current_model.json` 里存**当前降级级别**。
  这一点是**自查后改的**：最初用"原指针版本的文件是否还在"当"是否处于降级"的判据，
  但 L1 保留旧模型时旧文件**明明完好**，于是"从降级恢复"会被漏记、轨迹断裂。
  现改为读显式记录的 `level`。
- **不得静默**：原先有**两条失败路径完全不告警不落痕** ——
  ①「数据不足 → 提前 return」（此时 `train_meta.json` 根本没写，主流程的 `resolve()` 不会执行）；
  ②「未捕获异常 → 外层 except」。现两条统一走 `drl_train._degrade_on_failure()`。

### 5.2 ⚠ 自查发现并修掉的更危险模式：静默回退到**回测遗留模型**

`data/drl/<YYYYMMDD>/` 下**混放着两类**目录。实测盘点（2026-09-19，32 个）：

| 类别 | 数量 | 范围 |
|---|---|---|
| 有实盘标记（`pre_drl_brief.json`） | 12 | 2026-08-26 ~ 2026-09-08 |
| 无实盘标记 | 20 | 19 个回测/验证遗留（2015-06-12 ~ 2021-12-31）+ **实盘日 20260825** |

无标记的 20 个里，**有 7 个满足朴素"可用"判据**（`model.zip` + `train_meta.ok=True`）：
`20181019 / 20190628 / 20200323 / 20200630 / 20210210 / 20211231 / 20260825`。

⇒ 朴素"按日期倒序扫最近一个 ok=True"在**近端版本全不可用**时会回退到
**`20211231`** —— 一个 5 年前、由回测流水线产出的模型。这是"静默用错模型"，
**比 L3 告警危险得多**（L3 至少是响的）。已叠加**两道保险**：

1. `is_live_version()`：必须有实盘流水线独有的标记文件（`pre_drl_brief.json`，可 `DRL_LIVE_MARKER` 覆盖）；
2. `FALLBACK_LOOKBACK_DAYS = 45`：回退窗口只认"上一版"，不认"五年前那一版"。

被跳过者**计数留痕**（`skipped_not_live` / `skipped_out_of_window`）而非默默忽略 ——
万一将来判据失效，账本会显示"扫到 N 个但全部被跳过"，可直接定位，
而不是表现为一句无从排查的"无有效版本"。

**已知偏差（如实标注）**：实盘日 `20260825` 早于标记的引入，也会被判为"非实盘"
而排除在回退候选外。方向是**保守**的 —— 它是最老的实盘版本，只有 08-26~09-05
全不可用时才会被考虑，此时本模块选 L3 暂停（**可能误停**），不会静默用错。

### 5.4 明确**不做**的事（按用户要求）

「验证不通过」需要**统计阈值**，而阈值必须按 METHOD-1
（见 §📌 方法论固化）基于**下游表现**而非分布范围来定。
故本批次：`record_validation()` 只把每轮验证的**实际数值**落盘，且显式
`threshold_applied=false`；`resolve()` **不使用**它触发任何降级。
待积累 1-2 个月数据后再决策。

**参数漂移检查 —— 已实现（2026-09-19），只告警不阻断**

唯一"数据已就绪、只缺代码"的 DRL 项。实现要点：

| 项 | 实现 |
|---|---|
| 模块 | **`src/drl_drift.py`（轻量，不依赖 torch/gymnasium/stable_baselines3）** |
| 接线 | `drl_train` 在最终写盘前调 `drl_drift.check_weight_drift(meta, out_dir)` → 挂 `train_meta.weight_drift` |
| 动作 | **只告警不阻断**：超阈值仅 `warn_once("drl_weight_drift")`，不改权重、不拦当日 plan |
| 阈值 | `DRL_DRIFT_THRESHOLD`，默认 **0.3**，且记录里标注 `threshold_is_calibrated=False` |
| 两种漂移 | `drift_base_to_final`（单次训练推离基准）与 **`drift_day_over_day`**（与上一交易日比，真正要标定的量） |
| 账本 | 每条追加 `data/drl_weight_drift.jsonl`（`source=run` / `backfill` 可区分） |
| 回归 | `tests/test_drl_weight_drift.py` 11 例，**构造了超阈值与未超阈值两种触发条件** |

> **为什么必须独立成模块**：原先写在 `drl_train.py` 里，而后者导入即拉 torch ⇒
> ① 不装 torch 的 **CI core job 会收集失败**；② 报告脚本也被迫装全套 DRL 依赖。
> 拆出后测试与报告在无 torch 解释器下实测可用（该测试导入耗时 4.91s → 0.13s）。

**16 天回溯标定数据**（`scripts/drl_drift_report.py`，基于已落盘的 16 份 train_meta）：

| 漂移口径 | min | median | max | 阈值 0.30 命中 |
|---|---|---|---|---|

### 📌 方法论固化：边界/阈值必须由**下游表现**决定，而非**分布范围**

> 该坑在本项目已出现**两次**：`[0.10, 0.39]`（最初记错的）与 `[0.02, 0.40]`（新提议的）。
> 两次都是**从一个点/少量样本的分布范围**推出边界，而不是从"该值发生时的后果"推出。

**原则**：

1. 任何边界/阈值的设定，必须基于「**该值发生时的下游表现**」证据，**不是**「该值的分布范围」。
2. 分布只告诉你"它有多极端"，**不告诉你"它是否有害"**；有害与否只能由下游表现判断。
3. 正确顺序是：**先记录**（拿到发生频率与下游表现）→ **再评估**（有益还是有害）→ **才决策**
   （保留 / 截断 / 触发降级链）。
4. 证据不足时，**增加一个"零触发"的边界等于增加死代码**；宁可只记录。

**执行顺序（用户 2026-09-19 定）**：

```

                  DRL-5 最小版本：只记录极端权重，不截断（已完成）
下一批次（优先）：DRL-4 降级链（4 级）
                  DRL-3 学习后检查（新旧对比 / 验证集）
                  DRL-2 学习中指标落盘（entropy / policy_loss / grad_norm）
DRL-4 就位后：    用"极端值 + 下游表现"数据重新标定边界，再决定截断 / 降级 / 保留
```
