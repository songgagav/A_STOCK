# stockdb 厂商数据源: 已知状态与定位

> 建档 2026-09-22。本文回答三个问题: **三库为什么不补**、**厂商是否停更**、
> **数据源该以谁为主**。所有结论都附实测证据, 可直接复核。

| 问题 | 结论 |

| 厂商是否已停更? | **未确认, 但证据指向"需人核实授权/服务"**。详见 §3 |

## 2. 三个本地库: 为什么不补

### 实测状态

| 库 | 大小 | 文件数 | 最后写入 |
|---|---|---|---|
| `stockdb/data` | 21.3 GB | 672 | **2026-09-03 01:03:13** |
| `stockdb/data1` | 0.4 GB | 21 | **2026-09-03 01:03:13** |
| `stockdb/mydb` | 371 B | 6 | **2026-09-03 01:03:13** |

### 关键事实: 引擎的行情**不走**这三库

`stockdb/sync_url.txt` 写明: 「原理: **数据源 -> 同步数据 -> 你的/data**」,
源为 Cloudflare 后的 `a.123128.xyz`。实测:

- 三库 mtime 全停在 **09-03**;
- 同时 `stockdb.exe` 的 SDK(`pybao/stock_sdk.rd`)能返回 **09-21/09-22 的真实行情**
  (平安银行 09-22 收 11.71、浦发 9.04, `pre_close` 自洽);
- ⇒ **引擎走远端取数, 三库只是同步缓存**。

### 为什么"补"不划算

| 维度 | 分析 |
|---|---|
| 补的代价 | 必须先 `Stop-Service AStockStockdb` 释放 leveldb 独占锁 -> 跑更新器 -> 再启动。**代价是引擎停机** |
| 补的收益 | **0** —— 评估链路只读 h5i, 从不读这三个库(全仓检索确认: 仅在 `engine_bars_sync.py` 的文档注释里被提及) |
| 不补的风险 | **无**(引擎走远端) |

**决定: 不补。** 三库停在 09-03 是**已知状态, 不影响评估链路**。

### `data/LOCK` 的影响面(已评估)

leveldb 用 OS 独占文件锁, `stockdb.exe` 持有 `data/LOCK`。影响面**仅限**
「谁要写这三个库」—— 即 `数据更新.exe`。它不影响:

- 引擎的读(`rd.vals()`)—— 因为读的是远端;
- 本仓任何代码 —— 本仓不碰这三个库。

故无需为释放锁而停机。

## 3. 厂商是否停更: 证据与判断框架

### 实测证据

| 证据 | 指向 |
|---|---|
| 三库 mtime 停在 09-03(**约 20 天未写入**) | 同步链路已停 |
| `数据更新.exe` ExitCode=**0**、stdout/stderr **均 0 字节** | 「成功但什么都没做」 |
| 该进程约 **40 秒**后**静默驻留**(不退出、CPU 冻结在 10.2s、内存 29MB) | **等锁**或**等 GUI 交互**, 不是"同步失败" |
| 该进程**零网络连接** | 根本没尝试连接 |
| `log.txt` mtime 仍为 09-03, **未被写** | 更新器未进入工作阶段 |
| 主窗口标题 `数据更新`、`Responding=True` | 是 GUI 程序, 无头启动后等人操作 |

### 判断框架

**支持「厂商侧停更/授权到期」**: 20 天零写入 + 更新器零网络 + 日志未写。

**支持「本地锁/GUI 问题」**: 更新器有窗口且响应, 零输出 —— 更像卡在等待,
而非被服务端拒绝。**注意: 这一条削弱了"厂商停更"的推断**, 因为若是服务端拒绝,
通常会在 stdout/日志留痕。

> **诚实结论: 无法从本机证据区分这两者。** 要区分必须:
> ① 用管理员权限 + 图形界面跑一次更新器, 看有无交互提示(登录/续费);
> ② 查厂商文档 `stockdb/调用方式/` 确认有无**非交互式**同步接口;
> ③ 直接联系厂商确认授权状态。

### ⚠️ 一个重要的反面观察(2026-09-22 22:00 实测)

**"三库未写入"并不等于"数据没到"**: 同日引擎 SDK 已能返回 09-21/09-22 的
真实行情, 而三库仍是 09-03。故 **不能**用三库 mtime 推断"厂商是否发布" ——
它只反映**同步缓存**是否更新。

## 4. akshare 作为备选主源: 口径验证结果

### 验证方法

抽样 60 只在市标的(2026-09-18 由 h5i 取), 对比引擎与 akshare
`stock_zh_a_hist` 在**重叠日 09-18** 的 OHLC / 涨跌幅 / 成交量 / 成交额。

### 结果

| 维度 | 结果 |
|---|---|
| OHLC / 涨跌幅 逐值一致 | **15/16** |
| `volume` 比值(引擎/akshare) | **mean = 100.0001**, min 100.0000, max 100.0016 |
| `amount` 1:1 | **16/16** |
| 缺口日(09-21/09-22)可取 | **32/32** |

**口径换算(已确认)**:
- OHLC、`pct_chg`: **1:1**, 无需换算;
- `volume`: akshare 是**手**, 引擎是**股** ⇒ **×100**(实测比值 100.0000~100.0016);
- `amount`: **1:1**(单位: 元)。

### 那 1 例不一致: 600177 的复权口径

| | close | pre_close | pct_chg |
|---|---|---|---|
| 引擎 09-18 | 8.14 | **8.10** | **+0.49** |
| akshare(不复权) 09-18 | 8.14 | 8.30(隐含) | **−1.93** |

**引擎是自洽的**: `8.14 / 8.10 − 1 = +0.4938%` ✓, 与它自己的 `pct_chg` 相符。
而 akshare 不复权用 8.30 作前收(除权参考价)。⇒ **这是复权口径差异, 不是数据错误**。

**状态: 假设已强证据支持, 但未完成独立验证** —— akshare 在验证过程中触发限流
(`ConnectionError`, 约 80 次请求后), 未能取到 `adjust="qfq"` 对比确认。
**待办**: 限流恢复后用 `adjust="qfq"` 复核 600177 的涨跌幅是否等于引擎的 +0.49。

### 切换主源的前提(当前未满足)

1. 完成上述复权口径复核(至少抽样确认, 不能只看 1 例);
2. 确认 akshare 的**稳定性与限流行为**足以支撑每日全市场拉取;
3. 建立**双源交叉校验**再切换, 而不是直接替换。

**当前定位: `stockdb` 仍是主源**(引擎可用且数据已到 09-22);
**akshare 是已验证口径的备份源**, 随时可启用。

## 6. Baostock 口径验证与能力边界(2026-09-22 实测)

> 用户提议引入 Baostock 做历史补数。以下**逐项实测**, 并**纠正提议中的两处**。

### 6.1 口径: 与引擎**完全一致**(比 akshare 更好)

抽 **8 只标的 × 3 个交易日**(09-18/21/22), `adjustflag="3"`(不复权):

| 维度 | 结果 |
|---|---|
| OHLC **逐值一致** | **8/8 只 × 3 日, 全部一致** |
| `volume` 比值(引擎/baostock) | **min = max = mean = 1.0000** |
| `amount` | 1:1 |

⇒ **Baostock 的 volume 单位是「股」, 与引擎同口径, 不需要 ×100**
(这点与 akshare **相反** —— akshare 是「手」, 必须 ×100)。
**两源混用而不按源声明换算, 会得到差 100 倍的量且没有任何报错。**

### 6.2 ⚠️ 纠正提议: `adjustflag` 的取值

提议写「`adjustflag="2"` # 2=前复权(推荐)」。**实测三种取值的浦发 09-18 close**:

| adjustflag | close | 含义(**实测确认**) |
|---|---|---|
| `1` | **121.24** | **后复权**(价格被大幅放大) |
| `2` | 9.07 | **前复权** |
| `3` | 9.07 | **不复权** |

即 **1=后复权 / 2=前复权 / 3=不复权**(与 baostock 官方文档一致)。
**本仓对齐口径是 `3` 不复权**: 引擎 09-18 浦发 close = **9.07**, 与 flag=3 一致。
若按提议用 `2`, 在**无除权事件的区间**恰好也是 9.07(所以小样本看不出差别),
但一旦区间内有分红送转,**两者会分道扬镳** —— 这正是"小样本验证通过、上线才炸"的典型。

### 6.3 ⚠️ 纠正提议: 它是**逐 symbol** 接口, 无法按日批量

| 尝试 | 结果 |
|---|---|
| `query_all_stock(day)` | 返回 **7393 行**, 但字段只有 `code, tradeStatus, code_name` —— **不含 OHLCV** |
| 该接口是否给 `type`(区分个股/指数/ETF) | **不给**。要判断 `type` 必须**逐个**调 `query_stock_basic` |

⇒ **全市场每日取数 = 逐只 5481 次请求**。实测吞吐(**无间隔**连打 20 只):
**20/20 成功, 150 ms/只, 零限流**。推算:

| 间隔 | 全市场 5481 只 |
|---|---|
| 无间隔(**实测**) | **13.7 分钟** |
| 0.3s(实测上限 + 余量) | 27.4 分钟 |
| **1.5s(提议的限流间隔)** | **2.28 小时** |

> 好消息: 提议的 `1.5s` 比实测需要**保守得多**(实测 150ms 就能稳定跑)。
> **但即便是 13.7 分钟, 也无法承担"每日全市场"** —— 本仓收盘管道 19:10 启动、
> 窗口到 22:00, 而它还要跑选股/回测/训练; 再叠 14~27 分钟的单源取数不合理。
> 且识别哪些代码是**个股**(排除 ~1900 个 ETF/指数)还要再花 6897 次 `query_stock_basic`。

### 6.4 覆盖缺口: **北交所无数据**

`bj.430047` 等北交所代码 `query_stock_basic` 返回**空**。故 Baostock 只覆盖**沪深**。
本仓 h5i 里若有北交所标的(实测 09-22 全市场 5481 只含 `8*`/`4*` 前缀),
**Baostock 补不了**。

### 6.5 结论: 定位为「定向补数与交叉校验」, 不作每日主源

| 场景 | 推荐 | 理由 |
|---|---|---|
| **定向历史补数 / 缺口回填** | **Baostock** | 口径与引擎逐值一致、无需单位换算、限流宽松; 逐只取数对**少量标的**正合适 |
| **双源交叉校验** | **Baostock**(优于 akshare) | 口径一致 ⇒ 差异即真异常; akshare 还需先处理 ×100 与复权口径 |
| 每日全市场摄入 | **维持引擎(stockdb SDK)** | Baostock 逐只 13.7+ 分钟, 不适合每日管道 |
| 实时行情 | 引擎 / AkShare | Baostock **无实时数据** |
| 另类数据(龙虎榜/北向) | AkShare | Baostock 不覆盖 |

**已落地**: `baostock` 已登记进 `bars_ingest.SOURCE_SPECS`
(`volume_mult=1.0`, `symbol_strip_prefix=True` —— 它用 `sh.600000` 形式,
不剥前缀会**静默匹配不上**任何按裸代码查的东西), 归一化契约已由
`tests/test_bars_ingest.py::TestEveryRegisteredSourceSatisfiesTheContract` 对**每个源**自动验一遍。
