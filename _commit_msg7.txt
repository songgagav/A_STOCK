### ③ LESSON 巡检的具体形式**已落地**(用户推荐方案③, 附两点校准)

用户方向正确: 命中率直接回答「该加缓存还是改形态」。但**单独看命中率会误导** ——
一个**已被正确改成批量**的调用点命中率同样是 0%(它根本不查第二次)。故判据是组合:

```
n_calls 大 AND hit_rate 近 0  ->  键唯一, 该改查询形态   <== 真信号
n_calls 大 AND hit_rate 高    ->  键重复, 缓存有效/该加缓存
n_calls 小 / 耗时可忽略        ->  不报(否则制造噪声)
```

**命中率用 `1 - distinct_keys / n_calls` 定义, 不依赖缓存实现** ——
这样它对**未加缓存**的函数同样有定义(那正是最需要诊断的情形)。

实现: `src/access_probe.py`; 挂在**方法层**(`db.StockDB` 三个存取加 `@_probed`),
不挂调用点(调用点会随重构移动, 而指标必须跟着能力走);
`selector.select()` 每轮 reset 并把结论写进产物 `access_probe` 字段。

**全市场真跑实测**:
```
fn                calls  distinct  hit_rate  total_ms
get_bars           2809      2809      0.0%    2601.5
get_financials     2801      2801      0.0%    1801.1
get_valuation      2801      2801      0.0%      77.0
```

**报告口径是实测校准出来的(首版错了, 留档)**: 首版把「次数达标」也当进报告条件,
于是 `get_valuation` 经批量预热后**全池只花 77ms**(原 11.9 分钟)却因
`calls=2801` **仍被点名**并建议「请改查询形态」—— 而它**已经**改好了。
**优化完还被点名会训练人忽略报告**, 故改为: **耗时决定要不要报, 次数只用于解释原因**。

**判别力**: 两个场景同样 2809 次 × 200ms 但建议**相反**, 已写成断言。
16 例守卫全绿。

## 数据源路由: 设计已出, 摸底推翻了四处具体假设

文档: `docs/bars-source-router-design.md`。**原则认可**
(「所有源经同一写入路径进 h5i」), 但实测:

| 提议 | 实测 |
|---|---|
| 复用 `_write_to_h5i(df, source=...)` | **该函数不存在**; 真实落点是 `h5i_sync.append_daily_bars()` + `_df_to_h5i_table()` |
| 写入带 `source=` | 写入路径**不接受** `source`, 且 `daily_bars` **没有 source 列** |
| free-stockdb 本地 parquet `data/daily/xxx.parquet` | 本机**无此结构**; `stockdb/data` 是 **leveldb**(664 个 `.ldb`), 停在 09-03 |
| free-stockdb 与 stockdb 分别接入 | 本机它们是**同一个东西**(引擎实际走远端) |
| h5i-db CLI `create-table`/`ingest` | **无此 CLI**; 本仓用 Python `h5i_db.Database` API |
| AData / Baostock | **均未安装**(`adata=False, baostock=False`) |

### ⚠️ 最重要的一条新约束(提议未覆盖)

`append_daily_bars` 是**单调追加**, 只接受 `date > h5i 现有最大日期` 的行。
⇒ **「主源失败 → 备源兜底」只在『水位还没推过去』时成立**;
主源漏掉的、水位之前的历史缺口**无法**用 append 回填, 必须走
`h5i_ingest.py` / `h5i_rebuild.py`(运维动作, 非路由动作)。
故路由层必须显式返回 `unfillable_gap`, 否则会出现「以为备源补上了, 实际没写」。

另两条: 两道既有闸门(`data_quality_guard` 结构哨兵 + 单调追加)**必须保留**;
`akshare`/`h5i_db` 只在 `.venv310` 可用 ⇒ **数据摄入必须跑 .venv310**。

### 建议顺序: 先契约, 后源
阶段一抽源无关的 `bars_ingest.py`(纯重构, 测试锁等价) → 阶段二只接 **akshare**
做**双源交叉校验**(证明框架可用, 不急着扩源) → 阶段三按需扩源。
**未验证的源不进路由表**。
